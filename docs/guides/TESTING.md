## Что требуется от контрибьютора

**Новое поведение приезжает с тестом.** Правка, меняющая наблюдаемый результат (возвращаемые данные, статус-код, набор видимых зрителю данных), без теста не проходит ревью. Числового порога покрытия как цели нет: цель — покрытые ветки правил, а не процент. Но пороги существуют и роняют сборку: свой ратчет есть у бэкенда и у фронтенда. Правило ратчета одно на оба: поднимать после роста и никогда не опускать после падения. Осознанное удаление кода, уронившее число, называется в ревью, и числа возвращаются следом. Нижняя граница при этом есть и работает как трещотка: CI краснеет, когда покрытие падает ниже уже достигнутого уровня. Границу поднимают после роста и никогда не опускают ради зеленого прогона.

**Unit — вариант по умолчанию.** Он дешевый, быстрый и указывает на сломанное правило точно. Integration-тест пишется тогда, когда мок не способен доказать проверяемое утверждение.

| Утверждение | Почему unit не годится |
|--------------|------------------------|
| Форма HTTP-контракта: статус-код, envelope, заголовки | Мок сервиса не проходит через фильтры, мапперы и сериализацию |
| Трансляция запроса в SQL, фильтры soft-delete, пагинация, сортировка | Мок репозитория возвращает то, что попросили, а не то, что вернет БД |
| Пайплайн авторизации на реальном endpoint: гость, роль, владелец | Атрибуты и middleware в unit-тесте не исполняются |
| Уникальность, нумерация, конкурентная вставка | Инвариант обеспечивает БД, а не код |
| Транзакционная граница: откат при ошибке в середине операции | Мок не откатывает |

Все остальное — unit: ветки правил, валидация, маппинг, расчеты, обработка ошибок.

**Контекст на in-memory провайдере — тестовый дубль, а не ярус.** Он допустим,
когда утверждение касается запроса, который составляет код репозитория, и тот же
путь исполняется против Postgres эндпоинтным или репозиторным тестом, либо когда
дефект виден только на перечислении в порядке вставки. Все, что решает база —
ограничения, уникальность, коллация, индексы, полнотекст, транзакционная
граница — уходит в Testcontainers.

## Запуск тестов

### Backend

```bash
# Все тесты
dotnet test

# Конкретный проект
dotnet test test/DM.Domain.Forum.Tests

# С фильтром
dotnet test --filter "TopicService"

# С отчетом
dotnet test --logger "trx;LogFileName=results.trx"
```

**Прогон в один поток.** Integration-тесты поднимают контейнеры и работают
против общей базы, поэтому два одновременных `dotnet test` в одном рабочем
дереве бьются за нее и валят друг друга сотнями отказов подряд. Отказ выглядит
как настоящий: тесты падают массово и в разных контроллерах. Прежде чем искать
дефект в коде после такого прогона, убедиться, что второго процесса не было, и
повторить прогон в одиночку. Это же правило действует для агентов: параллельные
задачи бэкенда разводятся по времени, а не по проектам.

То же и с фронтендом, но по другой причине: юнит-тесты падают по таймаутам,
когда машина занята чем-то тяжелым. Push запускает хук, а хук — все гейты
разом, поэтому пуш во время идущего прогона тестов дает горсть отказов на
ровном месте. Пушить с незанятой машины; получив отказ, сначала повторить
прогон в тишине и только потом читать его как дефект.

### Frontend

```bash
cd src/DM.Web.Client

npm run test:coverage          # Все тесты один раз, с покрытием
npm run test:unit              # Watch mode
```

### E2E

```bash
cd src/DM.Web.Client

npm run test:e2e:fast    # один браузер (chromium) - его же гоняет CI
npm run test:e2e         # все браузерные профили, перед релизом
npm run test:e2e:ui      # интерактивный прогон
npm run test:e2e:debug   # пошаговая отладка
```

Скрипты в package.json - единственное определение того, как запускается e2e:
CI зовет тот же test:e2e:fast, а не собственную копию команды.

Ярус ходит в API по HTTP и проверяет то, что нарисовал браузер, поэтому ему нужен поднятый стек с сидом и выключенным лимитом запросов: `powershell -File .\scripts\dm.ps1 e2e` или `./scripts/dm.sh e2e` пересоздает API так же, как его запускает джоба e2e в CI ([Установка](./LOCAL_SETUP.md#команды)). Бандл конфиг собирает и поднимает сам: дев-сервер для прогона не годится и не переиспользуется, иначе измеряется чужая сборка.

Прогон идет в одном браузере. Остальные проекты конфига множат время, не проверяя ни одного нового утверждения, поэтому кросс-браузерная проверка живет отдельно от ревью. Тот же прогон делает хук перед пушем, последним из гейтов, с настройками джобы CI (`CI=1`: один воркер, два повтора, запрет `test.only`) и общим таймаутом в полчаса. Стенд хук не поднимает: он проверяет его первым делом и при отказе называет команду, которая его готовит.

Код возврата у набора честный. Строка "N did not run" в итоге прогона значит тесты из группы, чей `beforeAll` упал: сами они не запускались, а падение хука засчитано тесту, в котором хук выполнялся, и стоит в строке "failed" выше по выводу. Итог поэтому читается целиком, а не по хвосту.

## Backend Unit Tests

### Зеркальная структура

Тестовое дерево зеркалит production: тестовый проект на каждый production-проект, путь папки внутри тестового проекта повторяет путь тестируемого кода. Тест на новый класс кладется по зеркальному пути, а не в корень проекта.

Общие базовые классы и фикстуры не копируются по проектам — они живут в одном общем тестовом проекте. Билдеры тестовых данных лежат в `Dsl/` тестового проекта и собирают сущности fluent-методами: литеральные графы объектов в каждом тесте запрещены, иначе смена схемы правит сотни тестов вместо одного билдера.

Блюпринт дерева — [PATTERNS.md](../conventions/PATTERNS.md).

### Паттерн именования

Класс и метод вместе читаются одной фразой: `{Субъект}Should` плюс окончание
предложения.

```
PollVotingShould.RefuseASecondOptionToTheSameVoter
```

Фраза называет наблюдаемое поведение, а не вызванный метод и не механику
проверки. Условие входит в нее естественным придаточным там, где оно
существенно (`...WhenTheGameHasNoMaster`), а не отдельной секцией имени:
разделители из подчеркиваний дробят предложение и вынуждают повторять субъект,
который уже назван классом.

### Пример теста

```csharp
public class TopicServiceShould : UnitTestBase
{
    private readonly ITopicRepository _repository;
    private readonly TopicService _service;

    public TopicServiceShould()
    {
        _repository = Mock<ITopicRepository>();
        _service = new TopicService(_repository);
    }

    [Fact]
    public async Task RejectTopicWithEmptyTitle()
    {
        var createTopic = new CreateTopic { Title = string.Empty };

        var act = () => _service.CreateTopic(createTopic);

        await act.Should().ThrowAsync<HttpException>();
        await _repository.DidNotReceive().Create(
            Arg.Any<Topic>(), Arg.Any<CancellationToken>());
    }
}
```

Дубль здесь и есть сам интерфейс: отдельного объекта-обертки нет, поэтому в поле
лежит `ITopicRepository`, в конструктор сервиса уходит он же, и он же отвечает на
вопрос о полученных вызовах. Ответы задаются вызовом с последующим
`.Returns(...)`, вопросы - `Received(1)` и `DidNotReceive()`.

Хелпер `Mock<T>()` из `UnitTestBase` отдает новый дубль на каждый вызов, поэтому
дубль заводится один раз в поле: настройка, написанная через повторный вызов
хелпера, достанется экземпляру, которого сервис не видел.

Утверждение направлено на наблюдаемый результат, а не на настройку дубля. Тест, единственная проверка которого - что дубль вернул подготовленное значение, остается зеленым после удаления проверяемого кода и поэтому не считается тестом.

### CancellationToken в проверках

Токен в проверке задается матчером `Arg.Any<CancellationToken>()`, а не значением
`default`. Проверка с `default` сверяет токен с конкретным значением и совпадает
лишь пока сервис не прокидывает свой: в день, когда прокинет, отрицательная
проверка станет тавтологией и перестанет ловить лишний вызов, а положительная
упадет на ровном месте.

```csharp
// Правильно
await repository.DidNotReceive().Create(Arg.Any<Topic>(), Arg.Any<CancellationToken>());

// Неправильно: проверка держится на том, что токен пустой
await repository.DidNotReceive().Create(Arg.Any<Topic>(), default);
```

Проверка асинхронного метода ждет результата: без `await` вызов уходит в CS4014,
а предупреждения в сборке - ошибки.

## Frontend Tests

### Структура

Тесты колокейтятся рядом с исходником по слоям FSD:

```
src/
├── entities/{entity}/model/*.spec.ts   # Сторы и модели сущностей
```

```typescript
import { describe, it, expect } from 'vitest';
import { pluralize } from '@/shared/lib/utils/pluralize';

describe('pluralize', () => {
  it('picks the 2-4 form', () => {
    expect(pluralize(3, 'пост', 'поста', 'постов')).toBe('поста');
  });
});
```

## Matrix-тесты privacy-sensitive тегов

Тег, видимость которого зависит от прав зрителя, покрывается **матрицей**, а не одним happy-path тестом: по кейсу на каждую строку матрицы видимости — audience, роль зрителя, контекст (surface, per-post и per-room override'ы) и форма блока (с адресатами, без имени, битое написание). Сама матрица и правила — [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md); тест обязан покрыть ее целиком, включая audience, где тег вырезается безусловно.

Обязателен негативный кейс: зритель без права получает результат, по которому невозможно установить сам факт наличия скрытого блока (инвариант zero-information erase).

Тесты матрицы — серверные: проверяемое утверждение в том, что фильтрация произошла до сериализации. Клиентские тесты покрывают round-trip редактора, а не видимость.

Грамматику разметки держит общая таблица [bbcodeGrammar.cases.ts](../../src/DM.Web.Client/src/shared/lib/utils/bbcodeGrammar.cases.ts), и сверяться с ней обязаны два теста: серверный сверяет показ, сохранение и поисковую проекцию, клиентский конвертер редактора и проверку разметки. Новая форма тега или битой записи приходит строкой таблицы, а не проверкой в одном из двух тестов, иначе сервер и редактор разойдутся молча. Правило, которое таблица исполняет, записано в [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md#грамматика-разметки).

## Генеративные проверки разметки

Таблица держит записи, о которых кто-то подумал. Остальное держат генеративные проверки: тексты, собранные случайно из общего алфавита, и свойства, которые обязаны выполняться на любом из них. Они идут в обычных прогонах `dotnet test` и vitest и занимают секунды.

### Из чего собираются тексты

Алфавит один на обе стороны: [markupAlphabet.ts](../../src/DM.Web.Client/src/shared/lib/testing/markupAlphabet.ts). В нем пары тегов во всех регистрах и с параметрами, битые записи каждого вида, все написания `[private]`, `[noparse]` и `[code]`, скобки, кавычки, переводы строк, управляющие символы и символы направления, пробелы других видов, адреса, которые одни разборщики принимают, а другие нет, и длинные повторы, в том числе вложенность глубже, чем строит сервер. Сервер читает его как JSON между маркерами, так же как таблицу грамматики, клиент импортирует. Кусок, добавленный в алфавит, начинают пробовать обе стороны.

Генератор сервера лежит в `test/DM.Testing/Markup`: свой, на SplitMix64, чтобы один и тот же сид давал один и тот же текст на любой машине. Клиент собирает тексты через fast-check ([markupFuzz.ts](../../src/DM.Web.Client/src/shared/lib/testing/markupFuzz.ts)). Текстов два вида: "суп", где теги стоят парами вокруг сгенерированного, иногда без закрывающего, среди кусков любого вида, и правильная разметка, которую грамматика принимает целиком. Каждое слово текста уникально, `Q0001Q`, `Q0002Q` и так далее, поэтому проверка видит, какое слово дошло до какого читателя.

### Что проверяется

Скрытый текст не попадает к тому, кто не вправе его видеть (`BbMarkupPropertiesShould`, `SearchTextProjectionPropertiesShould`). Ответ, что скрыто, дает эталонное чтение правила `HiddenTextOracle`: маленькое, знает только `[private]` и `[noparse]` и написано по BBCODE_RENDERING.md, а не по коду. Каждый читатель каждой поверхности получает ровно слова, которые ему открывают блоки вокруг них, и ни одного другого. То же для текстового вида, безопасного встраивания и поиска, включая запасной путь поиска для текста, который разбор не строит. Считаются и сами блоки: сколько блоков читатель читает, столько он их и получает. Блок, которого читатель не читает, не оставляет следа: ответ не зависит от того, что блок держал и как был написан, и пустых тегов вокруг него не остается (`LeaveNoTraceOfABlockTheReaderDoesNotRead`), а блок, стоящий на отдельной строке, уходит вместе со строкой (`LeaveNoLineOfABlockTheReaderDoesNotRead`). Сохранение отвергает ровно то, что отвергает правило. Сам эталон сверяется со строками таблицы, у которых есть отказ.

Круг правки автора и превью сверяются с сервером через корпус-эталон [markupCorpus.golden.json](../../src/DM.Web.Client/src/shared/lib/testing/markupCorpus.golden.json). Его пишет серверный тест `BbMarkupCorpusShould`: для фиксированного набора сгенерированных текстов то, что видит автор на странице, что получает редактор автора, и что отвечает путь сохранения, а для каждого адреса алфавита, рисует ли страница его ссылкой, картинкой и упоминанием. Тот же тест при каждом прогоне пишет корпус заново в памяти и падает, если файл говорит другое, поэтому правка сервера, алфавита или генератора без обновленного корпуса краснеет. Клиентский [bbcodeProperties.spec.ts](../../src/DM.Web.Client/src/shared/lib/utils/bbcodeProperties.spec.ts) читает корпус и проверяет:

- превью показывает автору то, что показывает страница. Оба HTML читаются в одно нейтральное представление: куски текста и то, чем каждый нарисован. Прощаются только оговоренные отличия превью: тире как набрано, картинка общего чата без спойлера, скрытый блок вне игрового поста текстом;
- то, что сервер отдает редактору автора, после `htmlToBbcode` дает набранный текст с точностью до написания тегов самим редактором, переводы строк включая;
- проверка разметки называет отказ ровно там, где его делает сохранение, на той строке, которую называет отказ, и молчит на правильной разметке;
- адрес превью принимает тогда и только тогда, когда его принимает страница.

Круг визуального режима (`visualMode.spec.ts`) проверяется на самом Tiptap редактора. Правильная разметка после визуального режима показывает то же, что показывала. Любой суп сохраняет каждое слово за теми же читателями игрового поста: визуальный режим вправе переставлять теги (список перестроек в той же спецификации), но не вправе перенести слово через границу скрытого блока; подписи спойлеров, ссылки, упоминания и картинки считаются наравне со словами. Кусок алфавита, набранный в визуальном режиме в любое место правильной разметки, не дает ни одному читателю слова, которое редактор ему не показывал: образцом служит сам документ редактора, а текст, который сохранение отвергнет, не проверяется, потому что до читателя он не дойдет. Превью на любом тексте возвращает его как набрано и ничего не бросает.

Разбор линеен: сгенерированный текст, повторенный до десятков килобайт, стоит времени пропорционально длине, отдельно для страницы, текстового вида и пути сохранения на сервере (`BbParserCostShould`) и для проверки разметки и превью на клиенте.

### Как воспроизвести падение

Серверная проверка при падении уменьшает текст по кускам, пока он падает, и печатает самый маленький текст, причину и команду для повтора этого случая:

```bash
DM_MARKUP_SEED=17952614942118279855 dotnet test test/DM.Infrastructure.Core.Tests --filter ShowEveryReaderExactlyTheWordsTheBlocksLetThemRead
```

Клиентская печатает то же, что печатает fast-check: уменьшенный пример, `seed` и `path`. Повтор:

```bash
cd src/DM.Web.Client
DM_MARKUP_SEED=-155307970 DM_MARKUP_PATH="0:0:3" npx vitest run --root src/ shared/lib/utils/bbcodeProperties.spec.ts
```

По умолчанию у каждой проверки свой постоянный сид, и каждый прогон пробует одни и те же тексты. Чтобы поискать дальше, `DM_MARKUP_RUNS` задает число текстов, `DM_MARKUP_SALT` на сервере и `DM_MARKUP_SEED` на клиенте сдвигают набор. Корпус для такого поиска пишется в отдельный файл и читается клиентом оттуда же:

```bash
DM_MARKUP_CORPUS=/tmp/corpus.json DM_MARKUP_RUNS=4000 DM_MARKUP_SALT=a dotnet test test/DM.Infrastructure.Core.Tests --filter BbMarkupCorpusShould
cd src/DM.Web.Client && DM_MARKUP_CORPUS=/tmp/corpus.json npx vitest run --root src/ shared/lib/utils/bbcodeProperties.spec.ts -t corpus
```

После правки сервера, алфавита или генератора корпус пишется заново и коммитится вместе с правкой:

```bash
DM_MARKUP_CORPUS=write dotnet test test/DM.Infrastructure.Core.Tests --filter BbMarkupCorpusShould
```

### Что делать с находкой

Найденное чинится в коде, и минимальный текст приходит строкой в таблицу грамматики, парой в `authorEditRoundTrip.spec.ts` или отдельным тестом рядом с кодом. Генеративная проверка не получает исключений под конкретный текст. Если поведение, которое она нашла, правило не описывает и оно видимо читателю, это вопрос владельцу: такое исключение записывается в спецификации именем с причиной и снимается, когда вопрос решен.

## Чек-лист перед коммитом

Список гейтов не дублируется текстом: его держит `scripts/hooks/pre-push`, который включается один раз на клон командой `git config core.hooksPath scripts/hooks`.

Те же гейты, но заранее и по своей воле, гоняет `bash scripts/gates.sh` (с аргументом — только шаги, чье имя его содержит). Прогон занимает около двадцати минут и еще набор e2e сверху, ровно столько же стоит и упавший пуш, поэтому дешевле узнать до него. Совпадение двух списков проверяет архитектурный тест.

Гейты идут не все, а нужные изменениям. Карта `scripts/ci-paths.json` раскладывает измененные файлы по группам путей и называет джобы, которые нужны каждой группе, а читает ее один скрипт `scripts/ci-paths.mjs`. Его зовут джоба changes воркфлоу, хук и `scripts/gates.sh`. Карта у них одна, а база сравнения разная: хук берет коммиты против `origin/dev`, `scripts/gates.sh` рабочее дерево против `origin/dev`, CI изменения с последнего зеленого прогона ветки. Расходятся они в одну сторону: после красного пуша CI гонит упавшее снова, а хук смотрит только на новые коммиты и может его пропустить, так что локально проверяется не больше, чем в CI. Правка одних документов гоняет архитектурные тесты и юнит-тесты клиента. Правка клиента не трогает сборку и тесты решения, кроме файлов клиента, которые тесты .NET читают как данные: стили, таблицы разметки и корпус. Они стоят в карте отдельной группой и зовут сборку. Правка сервера гоняет все, кроме compose-topology, потому что юнит-тесты клиента читают серверное дерево. Путь, которого карта не знает, правка `docker/`, `scripts/`, `.github/` или `nginx.conf` клиента, клиент вместе с сервером, тег и ночной прогон по расписанию дают полный набор. Что запущено и что пропущено и почему, печатает отчет хука и summary джобы changes. Полный набор по своей воле дает переменная `DM_GATES_FULL=1` перед `git push` или перед `bash scripts/gates.sh`.

Здесь только то, чего хук проверить не может:

- [ ] Новый код покрыт тестами
- [ ] Нет flaky тестов
