# Тестирование DM3

Ярусы тестов, что требуется от правки, как запускать тесты и разбирать падения. Раннеры, названные здесь, сверяет с деревом DocumentedTestTiersShould, команды в блоках DocumentedCommandsShould, остальное держит ревью.

---

## Обзор

| Слой | Фреймворк | Назначение |
|------|-----------|------------|
| Backend Unit | xUnit + NSubstitute + AwesomeAssertions | Бизнес-логика: ветки правил, валидация, маппинг |
| Backend Integration | xUnit + Testcontainers | Контракт HTTP, трансляция в SQL, транзакции и очередь против настоящей базы в контейнере |
| Architecture | xUnit + ArchUnitNET | Конвенции дерева: слои, зависимости, текстовые гейты по исходникам |
| Frontend Unit | Vitest + Vue Test Utils | Компоненты, утилиты, BBCode |
| E2E | Playwright | Сценарии в браузере против поднятого стека |

---

## Что требуется от контрибьютора

Правка, меняющая наблюдаемый результат (данные ответа, статус-код, то, что видит зритель), приходит с тестом, который не мигает, иначе не проходит ревью. Цель покрытия в ветках правил, а не в проценте, но порог есть и роняет сборку: у бэкенда в [check-coverage.sh](../../scripts/check-coverage.sh), у клиента в [vite.config.ts](../../src/DM.Web.Client/vite.config.ts). Порог работает как храповик: его поднимают после роста и не опускают ради зеленого прогона, а удаление кода, уронившее число, называется в ревью, и покрытие возвращают следом.

Unit по умолчанию: он дешевый, быстрый и указывает на сломанное правило точно. Integration-тест пишется, когда мок не способен доказать утверждение.

| Утверждение | Почему unit не годится |
|--------------|------------------------|
| Форма HTTP-контракта: статус-код, envelope, заголовки | Мок сервиса не проходит через фильтры, мапперы и сериализацию |
| Трансляция запроса в SQL, фильтры soft-delete, пагинация, сортировка | Мок репозитория возвращает то, что попросили, а не то, что вернет БД |
| Пайплайн авторизации на реальном эндпоинте: гость, роль, владелец | Атрибуты и middleware в unit-тесте не исполняются |
| Уникальность, нумерация, конкурентная вставка | Инвариант обеспечивает БД, а не код |
| Транзакционная граница: откат при ошибке в середине операции | Мок не откатывает |

Все остальное unit: ветки правил, валидация, маппинг, расчеты, обработка ошибок.

Контекст на in-memory провайдере тестовый дубль, а не ярус. Он допустим, когда утверждение касается запроса, который составляет код репозитория, и тот же путь исполняется против Postgres эндпоинтным или репозиторным тестом, либо когда дефект виден только на перечислении в порядке вставки. Все, что решает база (ограничения, уникальность, коллация, индексы, полнотекст, транзакционная граница), уходит в Testcontainers.

## Запуск тестов

Прогоны не идут параллельно. Integration-тесты работают против общей базы, и два одновременных `dotnet test` в одном рабочем дереве валят друг друга так, что отказ выглядит настоящим: массово и в разных контроллерах. Юнит-тесты клиента так же падают по таймаутам на занятой машине. Массовый отказ сначала повторяют в одиночку и только потом читают как дефект.

### Backend

```bash
dotnet test
dotnet test test/DM.Domain.Forum.Tests
dotnet test --filter "TopicService"
```

### Frontend

```bash
cd src/DM.Web.Client

npm run test:coverage          # все тесты один раз, с покрытием
npm run test:conventions       # гейты из src/gates, без покрытия
npm run knip                   # неиспользуемые файлы, экспорты, типы и пакеты
npm run test:unit              # watch mode
```

### E2E

```bash
cd src/DM.Web.Client

npm run test:e2e:fast    # один профиль, chromium
npm run test:e2e         # все профили конфига, перед релизом
npm run test:e2e:ui      # интерактивный прогон
npm run test:e2e:debug   # пошаговая отладка
```

Скрипты package.json единственное определение запуска: CI, хук и `scripts/gates.sh` зовут тот же `test:e2e:fast`, а не свою копию команды. Остальные профили множат время, не проверяя нового утверждения, и ревью их не ждет.

Ярус ходит в API по HTTP и проверяет то, что нарисовал браузер, поэтому ему нужен поднятый стек с сидом и выключенным лимитом запросов. Его готовит команда `e2e` скриптов `dm.ps1` и `dm.sh` ([Установка](./LOCAL_SETUP.md#команды)). Бандл конфиг собирает и поднимает сам и дев-сервер не переиспользует, иначе измеряется чужая сборка.

На ветке набор гонит джоба e2e на PR. Она режет набор на куски флагом `--shard`, по куску на задание матрицы, у каждого куска свой стек, свой отчет и своя сводка повторов, а публикация ждет все куски. Локально хук гонит его только с `DM_GATES_FULL=1`, а `scripts/gates.sh` с `DM_GATES_FULL=1` или по имени шага, `bash scripts/gates.sh e2e`. С какими настройками и как читать итог, написано в шапке хука.

### Хук перед пушем

Изменения попадают в dev только веткой и PR: CI гоняется на PR, сливается только зеленое, squash одним коммитом. Хук `scripts/hooks/pre-push` (включение в [README](../../README.md)) отвергает прямой пуш в dev и main, а на пуше ветки гоняет дешевые и точные гейты: тест инструмента сравнения кода `scripts/visual/compare-code.test.mjs`, гейты клиента из `src/gates`, мертвый код клиента (knip), линт вместе с форматом, типы, формат и сборку решения в Release, архитектурные тесты. Какие из них нужны пушу, решает карта путей [ci-paths.json](../../scripts/ci-paths.json), одна для хука, `scripts/gates.sh` и джобы changes, и правка одних документов сборку не зовет. Юнит-тесты клиента целиком, тесты решения, покрытие, e2e и шаги на docker гонит CI на PR, он же гейт слияния. Весь набор локально дает `DM_GATES_FULL=1`. Тот же ответ до пуша дает `bash scripts/gates.sh`, с аргументом только шаги, чье имя его содержит. Состав наборов и причины пропусков живут в шапке хука.

## Backend Unit Tests

### Зеркальная структура

Тестовый проект зеркалит свой production-проект: путь папки внутри повторяет путь тестируемого кода, и тест на новый класс кладется по зеркальному пути, а не в корень проекта. Общие базовые классы и фикстуры не копируются по проектам, они живут в `test/DM.Testing`. Сущности собирают билдеры из папки `Dsl/` (общие в `test/DM.Testing`, свои у проекта, которому они одному нужны) fluent-методами. Литеральный граф объектов в тесте запрещен, иначе смена схемы правит сотни тестов вместо одного билдера.

Блюпринт дерева в [PATTERNS.md](../conventions/PATTERNS.md).

### Паттерн именования

Класс и метод вместе читаются одной фразой: `{Субъект}Should` плюс окончание предложения, например `PollVotingShould.RefuseASecondOptionToTheSameVoter`.

Фраза называет наблюдаемое поведение, а не вызванный метод и не механику проверки. Условие входит в нее придаточным там, где оно существенно (`...WhenTheGameHasNoMaster`), а не отдельной секцией имени: подчеркивания дробят предложение и вынуждают повторять субъект, уже названный классом.

### Дубли

Образец [TopicServiceTestBase](../../test/DM.Domain.Forum.Tests/Dsl/TopicServiceTestBase.cs). Дубль NSubstitute и есть сам интерфейс: он лежит в поле, уходит в конструктор сервиса и отвечает на вопрос о полученных вызовах. Ответы задаются вызовом с `.Returns(...)`, вопросы `Received(1)` и `DidNotReceive()`.

Хелпер `Mock<T>()` из `UnitTestBase` отдает новый дубль на каждый вызов, поэтому дубль заводится один раз в поле: настройка через повторный вызов хелпера достанется экземпляру, которого сервис не видел.

Утверждение направлено на наблюдаемый результат, а не на настройку дубля. Тест, единственная проверка которого в том, что дубль вернул подготовленное значение, остается зеленым после удаления проверяемого кода и поэтому тестом не считается.

### CancellationToken в проверках

Токен в проверке задается матчером `Arg.Any<CancellationToken>()`, а не значением `default`. Проверка с `default` совпадает, лишь пока сервис не прокидывает свой токен. Когда прокинет, отрицательная проверка станет тавтологией и перестанет ловить лишний вызов, а положительная упадет на ровном месте.

Проверка асинхронного метода ждет результата: без `await` вызов дает CS4014, а предупреждения в сборке ошибки.

## Frontend Tests

### Структура

Spec лежит рядом с исходником ([PATTERNS.md](../conventions/PATTERNS.md)). Проверки, которые не принадлежат одному модулю, лежат в папке гейтов `src/gates`, и что ловит каждая, записано в ее [реестре](../../src/DM.Web.Client/src/gates/README.md).

Обвязка спека лежит рядом с ним и названа по его предмету. `X.doubles.ts` держит только подмены (`vi.fn` и фабрики), подменяемых модулей не импортирует, а `vi.mock` берет их фабрикой `async () => (await import("./X.doubles")).имя()`. `X.fixtures.ts` держит данные и монтирование. Хуки обвязка не вешает, а отдает спеку. Общие заглушки лежат в `shared/lib/testing`, по своему пути и без индекса, как заглушка окна `vueFinalModalStub.ts`. Оба вида файлов исключены из `tsconfig.app.json` и из покрытия, как сами спеки.

## Matrix-тесты privacy-sensitive тегов

Тег, видимость которого зависит от прав зрителя, покрывается матрицей, а не одним happy-path тестом: по кейсу на каждую строку матрицы видимости из [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md): audience, роль зрителя, контекст (surface, per-post и per-room override'ы) и форма блока (с адресатами, без имени, битое написание), включая audience, где тег вырезается безусловно.

Обязателен негативный кейс: зритель без права получает результат, по которому нельзя установить сам факт наличия скрытого блока (zero-information erase). Содержимое блока в таком кейсе полное (текст, картинка, ссылка, спойлер, цитата, вложенные теги, переносы строк), а остаток сверяется целиком: он один и тот же при любом содержимом, длине и адресатах блока.

Тесты матрицы серверные: утверждение в том, что фильтрация произошла до сериализации. Клиентские тесты покрывают round-trip редактора, а не видимость.

Новая форма тега или битой записи приходит строкой общей таблицы грамматики, а не проверкой в серверном или клиентском тесте, иначе сервер и редактор разойдутся молча. Таблица и два теста, которые с ней сверяются, описаны в [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md#грамматика-разметки).

## Генеративные проверки разметки

Таблица грамматики держит записи, о которых кто-то подумал. Остальное держат генеративные проверки: тексты, собранные случайно из общего алфавита, и свойства, которые обязаны выполняться на любом из них. Они идут в обычных прогонах `dotnet test` и vitest.

### Из чего собираются тексты

Алфавит один на обе стороны, [markupAlphabet.ts](../../src/DM.Web.Client/src/shared/lib/testing/markupAlphabet.ts): кусок, добавленный в него, начинают пробовать и сервер, и клиент. Генератор сервера в `test/DM.Testing/Markup` свой, чтобы один сид давал один текст на любой машине, клиент собирает тексты через fast-check в [markupGenerator.ts](../../src/DM.Web.Client/src/shared/lib/testing/markupGenerator.ts). Каждое слово текста уникально, поэтому проверка видит, какое слово дошло до какого читателя. Состав алфавита и виды текстов описаны в шапках этих файлов.

### Что проверяется

- Скрытый блок не попадает к тому, кто не вправе его видеть, ни на одной поверхности, ни в текстовом виде, встраивании и поиске (`BbMarkupPropertiesShould`, `SearchTextProjectionPropertiesShould`). Что скрыто, отвечает эталон `HiddenTextOracle`, написанный по BBCODE_RENDERING.md, а не по коду. Блок, которого читатель не читает, не оставляет следа.
- Сохранение отвергает ровно то, что отвергает правило.
- Превью, проверка разметки (с ней и строка, на которую указывает отказ сохранения) и прием адресов на клиенте сверяются с сервером через корпус [markupCorpus.golden.json](../../src/DM.Web.Client/src/shared/lib/testing/markupCorpus.golden.json). Его пишет `BbMarkupCorpusShould`, и этот тест краснеет, когда файл расходится с сервером, алфавитом или генератором. Читает его [bbcodeProperties.spec.ts](../../src/DM.Web.Client/src/shared/lib/bbcode/bbcodeProperties.spec.ts), оговоренные отличия превью перечислены в шапке [bbcodeToHtml.ts](../../src/DM.Web.Client/src/shared/lib/bbcode/bbcodeToHtml.ts).
- Визуальный режим редактора не переносит слово через границу скрытого блока (`visualMode.spec.ts`, допустимые перестройки там же).
- Разбор линеен по длине текста: `BbParserCostShould` на сервере, раздел "the cost of reading" в bbcodeProperties.spec.ts на клиенте.

### Как воспроизвести падение

Серверная проверка уменьшает текст, пока он падает, и печатает самый маленький текст, причину и готовую команду повтора. Клиентская печатает то, что печатает fast-check: уменьшенный пример, `seed` и `path`. Повтор:

```bash
cd src/DM.Web.Client
DM_MARKUP_SEED=-155307970 DM_MARKUP_PATH="0:0:3" npx vitest run --root src/ shared/lib/bbcode/bbcodeProperties.spec.ts
```

По умолчанию сид у каждой проверки постоянный, и прогон пробует одни и те же тексты. Чтобы поискать дальше, `DM_MARKUP_RUNS` задает число текстов, `DM_MARKUP_SALT` на сервере и `DM_MARKUP_SEED` на клиенте сдвигают набор. Корпус для такого поиска пишется в отдельный файл, и клиент читает его оттуда же:

```bash
DM_MARKUP_CORPUS=/tmp/corpus.json DM_MARKUP_RUNS=4000 DM_MARKUP_SALT=a dotnet test test/DM.Infrastructure.Core.Tests --filter BbMarkupCorpusShould
cd src/DM.Web.Client && DM_MARKUP_CORPUS=/tmp/corpus.json npx vitest run --root src/ shared/lib/bbcode/bbcodeProperties.spec.ts -t corpus
```

После правки сервера, алфавита или генератора корпус пишется заново и коммитится вместе с правкой:

```bash
DM_MARKUP_CORPUS=write dotnet test test/DM.Infrastructure.Core.Tests --filter BbMarkupCorpusShould
```

### Что делать с находкой

Найденное чинится в коде, а минимальный текст приходит строкой в таблицу грамматики или отдельным тестом рядом с кодом. Генеративная проверка не получает исключений под конкретный текст. Если найденное поведение правило не описывает и оно видимо читателю, это вопрос владельцу: такое исключение записывается в спецификации именем с причиной и снимается, когда вопрос решен.
