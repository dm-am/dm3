# Мониторинг DM3

Где смотреть логи, трассы, метрики и алерты и как найти замолчавшее звено. Метки и запросы LogQL сверяет LogDeliveryVisibilityShould, адрес внешней пробы сверяет DeploymentConfigurationShould.

---

## Адреса

| Что | Адрес |
|-----|-------|
| Grafana, логи, трассы и метрики | http://localhost:3000, пароль `GF_SECURITY_ADMIN_PASSWORD` из `docker/.env` |
| Prometheus | http://localhost:9090, цели на http://localhost:9090/targets |
| Jaeger | http://localhost:16686, прием OTLP gRPC на порту 4317 |
| Alertmanager | http://localhost:9093 |
| Loki, только API | http://localhost:3100 |
| Mailpit, только стенд | http://localhost:8025 |

Порты задает [`docker/docker-compose.yml`](../../docker/docker-compose.yml).
Все служебные интерфейсы, включая порт S3 хранилища и порты воркеров,
публикуются на `127.0.0.1`. Брандмауэр границей не служит: опубликованный
докером порт идет через цепочки nat/DOCKER и FORWARD мимо INPUT, поэтому граница
одна, адрес привязки. С другой машины смотреть через SSH-туннель, например
`ssh -N -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 user@server`.

## Логирование (Serilog)

Синки, энричеры и уровни заданы в
[`LoggingConfiguration.cs`](../../src/DM.Infrastructure.Core/Logging/LoggingConfiguration.cs).
Агента-сборщика нет, Serilog отправляет пакеты в Loki по HTTP сам.

Loki индексирует метки, а не текст строки, поэтому меток три: `app` и `env`
объявлены при настройке, `level` синк добавляет сам, строчными словами Grafana
(`error`, `warning`, `info`). Пользователь, корреляционный токен, длительность
остаются в теле строки и отбираются фильтром LogQL. Метка на величину с большим
числом значений размножает потоки без предела и делает Loki медленным. Уровня в
теле строки нет, он живет только меткой, и разбор тела через `| json` его не
найдет.

Вторая копия логов лежит на диске у докера, с потолком и ротацией, и только она
переживает отказ Loki. Поэтому вне Development консоль пишется машинным
форматом: шаблон для человека теряет свойства события, пользователя, токен и
трассу.

### Уровень

Уровень один на оба синка и задается переменной `LOG_MINIMUM_LEVEL`. Пусто
значит Debug в Development и Information в остальных окружениях. Для
Debug-строк при разборе инцидента меняют только эту переменную: окружение
`Development` заодно публикует Swagger, разрешает inline-скрипты и снимает HSTS.
Применяется рестартом. Значение вне перечня Serilog останавливает старт.

### Где смотреть

Grafana, Explore, датасорс Loki. `TraceId` в строке лога служит ссылкой в
трассу Jaeger (derived field в
`docker/grafana/provisioning/datasources/datasources.yml`).

### Полезные запросы (LogQL)

```
# Ошибки API. Fatal включен явно: отбор по одному "error" пропускает
# ровно тот случай, ради которого сюда идут
{app="DM.API", level=~"error|fatal"}

# Все строки одного корреляционного токена. Только API: токен живет в
# HTTP-запросе и через очередь не передается
{app="DM.API"} |= "1b2c3d4e"

# Сквозной поиск по всем приложениям идет по TraceId, контекст трассы едет
# в заголовках сообщения. TraceId лежит в той же строке, что и токен
{app=~"DM.+"} |= "4bf92f3577b34da6a3ce929d0e0e4736"

# Поток одного воркера
{app="DM.Notifications.Consumer"}
```

Срок хранения задан в [`docker/loki/loki.yaml`](../../docker/loki/loki.yaml)
(`retention_period`), удаляет компактор.

## Tracing (OpenTelemetry)

Инструментация задана там же, в `LoggingConfiguration.cs` (`WithTracing`). В
Jaeger сервис называется именем приложения (`DM.API`), а не именем контейнера,
трасса ищется по `TraceId` из лога.

Трассы живут в памяти коллектора. Тома нет, перезапуск контейнера обнуляет
хранилище, а глубина ограничена `max_traces` в compose: без потолка коллектор
упирается в лимит памяти, и его убивают вместе со всем, что он держал. За
пределами этого окна разбор идет по логам.

## Metrics (Prometheus)

`/metrics` и `/_health` есть на каждом .NET сервисе, на порту основного трафика.

Цели перечислены в [`docker/prometheus.yml`](../../docker/prometheus.yml). Хост
в `targets` обязан совпадать с `container_name` из compose, иначе цель остается
в списке с `up == 0`, и это ловят правила вида `ConsumerDown`. Имя job обязано
совпадать с job-селекторами правил и панелей: у переименованной job серии `up`
нет вовсе, правило на `up == 0` молчит, и этот случай закрывают правила на
`absent()`, например `ConsumerScrapeTargetMissing`.

Объектное хранилище отдает метрики через свой прокси, `dm-storage:9324`. Сайт
работает без хранилища, отказывают только загрузки и картинки, поэтому о
лежащем хранилище говорит только `ObjectStorageDown`.

Панели Grafana подключаются автоматически из
[`docker/grafana/dashboards/`](../../docker/grafana/dashboards/), готовые
выражения PromQL брать оттуда. Серии HTTP названы по OpenTelemetry
(`http_server_request_duration_seconds`).

## Alerting

Правила, пороги и окна `for` живут только в
[`docker/prometheus/alerts.yml`](../../docker/prometheus/alerts.yml), у каждого
правила там `summary` и `description`.

Правила вычисляет Prometheus, а не Grafana, поэтому канал уведомлений Grafana к
ним не привязать. Маршрут, группировка и получатель живут в
[`docker/prometheus/alertmanager.yml`](../../docker/prometheus/alertmanager.yml).
Письма уходят через relay писем приложения (`MAIL_HOST`, `MAIL_PORT`), отдельного
секрета у алертов нет, на стенде их видно в Mailpit. Получателя, отправителя,
логин relay и STARTTLS задает файл окружения, перечень с умолчаниями в
`docker/.env.example`. Alertmanager переменные окружения не читает, их
подставляет в шаблон при старте `docker/alertmanager-init.sh`.

На сервере `MAIL_HOST` обязателен, и `docker/scripts/init-env.sh server` без
него останавливается. Умолчание compose это Mailpit стенда, и сервер с ним
отправлял бы в тупик и письма сайта, и все алерты при исправном на вид контуре.

Правило `Watchdog` срабатывает всегда и приходит своим маршрутом с интервалом
из `alertmanager.yml`. Его приход доказывает, что правила вычисляются, маршрут
работает и почта уходит. Остальные правила молчат, когда сломан сам контур, и
тогда молчание неотличимо от здоровья. Кто следит за отсутствием `Watchdog`,
сказано в разделе о наблюдении снаружи машины.

## Production

### Наблюдение снаружи машины

Наблюдатель на наблюдаемой машине о собственной смерти не сообщит, поэтому
внешний сервис берет на себя две обязанности.

1. Опрашивать `https://<адрес>/_ready`, а не `/_health`. Живость отвечает
   зеленым у процесса, который не дотягивается ни до одной базы, готовность
   спрашивает Postgres. Порог две-три неудачные пробы подряд, иначе каждая
   выкладка читается как авария. Релиз, отвечающий 500 на содержательных
   маршрутах, готовностью не ловится.
2. Замечать молчание `Watchdog`: фильтр в почте, напоминание в телефоне или
   внешний сервис heartbeat. Заметить отсутствие может только тот, кто ждал
   прихода.

Край отдает `/_health` и `/_ready` мимо Basic Auth
(`docker/nginx/edge-locations.conf`). На имени домена после выпуска сертификата
80 порт отвечает только челленджем центра сертификации и редиректом на https,
поэтому проба идет по https. Как край отвечает по голому IP, описано в
[DEPLOYMENT.md](./DEPLOYMENT.md).

## Troubleshooting

### Логи не появляются в Loki

1. Loki готов: `curl http://localhost:3100/ready`
2. Поток создан: `curl -s http://localhost:3100/loki/api/v1/label/app/values`
3. Потока нет, тогда смотреть консоль (`docker logs dm-api`). Она пишет всегда,
   так что при мертвом Loki теряется только поисковая копия. Там же строки
   `SelfLog` в stderr на каждую отклоненную пачку, с кодом ответа Loki
4. Отказ хранилища виден и без логов: цель `loki` в Prometheus и правило
   `LogStorageDown`. Отклоненная пачка при живом хранилище (просроченный сэмпл,
   переполненная очередь синка) видна только через `SelfLog`

### Jaeger не показывает трассы

1. Проба зеленая: `docker inspect --format '{{.State.Health.Status}}' dm-jaeger`
2. Трассы доходят: `curl http://localhost:16686/api/services` перечисляет
   `DM.API`. Пустой список при живом приложении значит, что до коллектора не
   доехало ничего, а не что потерялась одна трасса
3. Переменная окружения `DM_ConnectionStrings__TracingEndpoint`
