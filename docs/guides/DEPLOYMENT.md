# Развертывание DM3

Как поставить, обновить и откатить стенд на сервере. Правила стенда по файлам `docker/` держат классы деплоя в `test/DM.Architecture.Tests`, по одному на предмет, остальное держит ревью.

Состав стенда и путь запроса через край описаны в [SYSTEM.md](../architecture/SYSTEM.md), раздел "Топология рантайма".

## CI/CD (GitHub Actions)

Сборка, тесты и публикация образов идут в `.github/workflows/dotnet.yml` на push и PR в `main` и `dev` и раз в неделю, на теги не запускаются. Сканы безопасности `security.yml` (CodeQL, baseline OWASP ZAP) вызываются из этого графа, и публикация образов их ждет. Раз в неделю `security.yml` запускается и сам по себе, полным сканом. ZAP сканирует API напрямую, без края и SPA, поэтому HTML-документ и заголовки края этим гейтом не проверяются.

Образы уходят в GHCR под префиксом `IMAGE_PREFIX`, и имя каждого обязано совпадать с тем, что тянет `docker/docker-compose.yml`. Каждый образ получает тег из короткого sha коммита без приставки (пустой `prefix` у `docker/metadata-action`), на этот формат опирается откат. Подвижные имена (`latest` и `main` с main, `dev` с dev) ставит джоба `promote-images` после публикации всех образов прогона, по их дайджестам и только когда аттестация каждого сходится с веткой и коммитом прогона.

## Docker Build

Бэкенд собирается по [`docker/app.Dockerfile`](../../docker/app.Dockerfile) и работает от пользователя `dmuser`, фронтенд по [`src/DM.Web.Client/Dockerfile`](../../src/DM.Web.Client/Dockerfile). Кэша сборки между прогонами нет ни у одной джобы: джобы публикации и проверочные джобы, которые идут через `docker compose up --build`, собирают образ с нуля.

## Развертывание на VPS

### Установка

Сервер ставится из клона на теге релиза, подпись которого оператор проверил ключом владельца. Из трубы установщик не запускается: от root работает то дерево, чью подпись проверили.

```bash
git clone --branch <тег> https://github.com/dm-am/dm3.git && cd dm3
git -c gpg.ssh.allowedSignersFile=<allowed_signers> verify-tag <тег>
sudo bash docker/setup-server.sh --signers <allowed_signers> --tag <тег> --mail-host <хост> --mail-port <порт>
```

`--signers` называет файл `allowed_signers` с ключом, которым подписываются релизы. Сервер принимает только теги, подписанные этим ключом. Без `--signers`, `--tag`, `--mail-host` и `--mail-port` установщик останавливается до того, как что-то поставит. Хостовая часть в [`docker/setup-server.sh`](../../docker/setup-server.sh), раскладка каталогов и первый релиз в [`docker/scripts/install-release.sh`](../../docker/scripts/install-release.sh), шаги перечислены там по порядку.

Пароль Basic Auth с логином `preview` установщик спрашивает сам. За ним стенд отвечает по `http://<IP>`, пока нет домена. Файл `.htpasswd` в репозитории не хранится, его создает [`docker/scripts/init-htpasswd.sh`](../../docker/scripts/init-htpasswd.sh). В конце установщик включает таймер выпуска, живой релиз показывает `sudo dm3-release status`.

Повторный запуск установщика обновлением не служит: если `/opt/dm3`, `/etc/dm3` или `/var/lib/dm3` не пусты, он отказывается работать, ничего не изменив. Локальный стенд описан в [LOCAL_SETUP.md](./LOCAL_SETUP.md).

### Стенд preview

Сайт целиком живет в оверлее: базовый compose дает инфраструктуру и API, [`docker/docker-compose.preview.yml`](../../docker/docker-compose.preview.yml) добавляет nginx и контейнер SPA. Поэтому любая команда, поднимающая или гасящая стенд, называет оба файла. На сервере такая команда одна, в скрипте выпуска [`docker/scripts/release-entry.sh`](../../docker/scripts/release-entry.sh), а юнит `docker/dm3.service` зовет его `boot` и `stop`. Расхождение ловит `scripts/deployment/check-compose-topology.sh`.

Дерева для правки на сервере нет. Каждый релиз лежит своим каталогом в `/opt/dm3/rel` и после создания не меняется, живой называет ссылка `current`. Файл окружения `shared/env` и учетные данные края `shared/edge` ведет оператор. Их пишут скрипты из `docker/scripts`, запущенные из `/opt/dm3/rel/current/docker`: рядом с релизом они сами пишут в `shared`. Устройство раскладки описано в шапке скрипта выпуска.

Стенд поднимается без сборки. На сервере каждый образ приложения назван дайджестом из `release.env` своего релиза, в клоне и на точке присутствия образы берутся по одному тегу `IMAGE_TAG`, потому что собраны они одним прогоном.

Пароль Basic Auth меняет тот же скрипт: `sudo bash /opt/dm3/rel/current/docker/scripts/init-htpasswd.sh`, затем `sudo docker restart dm-nginx`. Скрипт заменяет файл новым, а край читает его только при старте.

### Выпуск релиза

Релиз это подписанный тег `vMAJOR.MINOR.PATCH` на коммите `dev`, который CI уже собрал, аттестовал и опубликовал. Сервер берет только такие теги и разворачивает ровно те четыре образа, чьи дайджесты названы в теге. Тег пишет и пушит команда [`scripts/release/release.sh`](../../scripts/release/release.sh), чего она не подпишет, перечислено в ней самой.

Подписывает владелец своим SSH-ключом, с появлением первого сервера. До того теги релиза не ставятся.

На машине нужны git 2.34 или новее, OpenSSH 8.2 или новее, git с `gpg.format ssh` и `user.signingkey`, `gh` после `gh auth login`, docker с buildx и право пуша в репозиторий. Ключ лучше аппаратный, с касанием на каждую подпись.

Порядок.

1. Отдельный чистый worktree на последнем теге релиза, без хуков: `git -c core.hooksPath=/dev/null worktree add --detach ../dm3-release <тег>`. Подпись тега проверяется своим ключом: `git -c gpg.ssh.allowedSignersFile=<файл с ключом> verify-tag <тег>`. Команда сама сверяет, что дерево чистое и стоит на этом теге, но подпись остается за человеком.
2. Прочитать `git diff <тег> origin/dev -- scripts/release scripts/lib/attestation.sh`. Подписывает команда из worktree, и правка в ней, пришедшая после тега, подписала бы чужие дайджесты. Изменения входят в релиз после того, как прочитаны.
3. Из worktree: `bash scripts/release/release.sh v1.4.0`. Без второго аргумента берется вершина `origin/dev`, коммит можно назвать явно. Команда печатает текст тега, подписывает его, проверяет свою подпись, пушит один тег и выходит.

Чем кончился выпуск, сервер сообщает письмом. Команда его не ждет.

### Обновление стенда

Сервер ставит только подписанные релизы, все через `dm3-release`. Глаголы и что каждый делает перечислены в шапке [`docker/scripts/release-entry.sh`](../../docker/scripts/release-entry.sh), команды даются от root.

- `poll` зовет таймер `dm3-release.timer` каждые пять минут: берет старший новый подписанный тег и выкатывает его без простоя через близнецов API и фронтенда.
- `deploy <тег>` выкатывает один тег вне очереди таймера.
- `rollback` возвращает релиз, который заменил живой.
- `maintain <тег>` ставит проверенный тег с простоем. Флаг `--reset-database` стирает базу стенда, он нужен релизу, меняющему схему.
- `recover` поднимает то, что называет `current`, и ставит край на основные экземпляры.
- `boot` и `stop` зовет юнит `dm3`, `status` показывает живой релиз и состояние контейнеров.

Без простоя выпускается только приложение. Новый образ края, правило тревоги, дашборд, настройка PostgreSQL, правка скрипта из `docker/scripts`: такой релиз таймер отвергает, о нем приходит письмо, и оператор ставит его командой `maintain` с простоем того, что перезапускается.

Версии только растут, и каждый тег пробуется один раз. После отказа исправление выходит новой версией, и следующий тег пушится только после письма о предыдущем. Письма это тревоги `Release*` из [`docker/prometheus/alerts.yml`](../../docker/prometheus/alerts.yml).

Релиз, меняющий схему, автоматический путь не берет, пока действует правило единственной `InitialCreate` ([DATA_STORAGE.md](../conventions/DATA_STORAGE.md), раздел "Миграции"). Его ставит `maintain <тег> --reset-database`.

После выпуска стенд проверяется прогоном `docker/scripts/smoke-edge.sh` против публичного адреса.

Какой релиз писал лог, видно из свойства `Release` каждой строки: CI передает коммит в сборку аргументом `SOURCE_REVISION`. Образ, собранный без него (локальный `docker compose up --build`), пишет `unknown`.

### Край держит адреса с момента старта

Имена контейнеров nginx разрешает один раз, при разборе конфигурации, без `resolver` намеренно (причина в [`docker/nginx/nginx.conf`](../../docker/nginx/nginx.conf)). Поэтому после замены любого контейнера за краем край перечитывает конфигурацию или пересоздается, иначе отвечает 502 на адрес, которого больше нет. Для того, что меняет скрипт выпуска, это делают выкатка, `maintain` и `recover`. Для остального (хранилище `storage`, рендерер картинок, ручной `--force-recreate`) это обязанность того, кто пересоздает.

### HTTPS

Появляется вместе с доменом, до него стенд отвечает по http. Самоподписанного сертификата не будет: предупреждение браузера учит кликать сквозь предупреждения.

Сертификат выпускает `sudo bash /opt/dm3/rel/current/docker/scripts/init-ssl.sh <домен>` через webroot, край при этом не останавливается. Затем:

```bash
sudo systemctl restart dm3
sudo certbot renew --dry-run                # продление отрабатывает без участия оператора
```

Почему webroot, а не плагин `--nginx`, сказано в [`docker/scripts/init-ssl.sh`](../../docker/scripts/init-ssl.sh). Редирект на https скрипт вешает на имя домена, и по IP стенд отвечает как раньше.

### Точка присутствия

Второй публичный адрес обслуживает обратный прокси без приложения и без секретов, он описан в [POINT_OF_PRESENCE.md](./POINT_OF_PRESENCE.md) вместе с командой запуска. Файл окружения на нем создается из `docker/.env.pop.example`, а не из `docker/.env.example`: тот везет на машину в чужой юрисдикции все пароли из репозитория (`PointOfPresenceShould`). Край точки присутствия подчиняется тому же правилу края.

## Переменные окружения

Переменные приложения задает якорь `x-workload-env` в [`docker/docker-compose.yml`](../../docker/docker-compose.yml). Серверный `shared/env` создает `docker/scripts/init-env.sh server`: генерирует ключ шифрования и все секреты, ставит `ASPNETCORE_ENVIRONMENT=Production` и режим схемы. Переменные скрипта выпуска перечислены в [CONFIGURATION.md](../references/CONFIGURATION.md#выпуск-на-сервере). Копия `docker/.env.example` руками оставляет пароли из репозитория и пустой ключ, на котором compose не стартует.

Имя бакета после установки не меняется: `STORAGE_BUCKET` задают один раз, до первого старта. На томе с данными другое имя создает второй, пустой бакет, healthcheck остается зеленым, а старые картинки перестают открываться. Переименование бакета и переезд в другое S3-хранилище идут как восстановление из бэкапа.

## Откат

| Метод | Команда |
|-------|---------|
| Релиз | `sudo dm3-release rollback` |
| PostgreSQL | `gunzip -c /var/backups/postgresql/<файл>.sql.gz \| docker exec -i dm-pg psql -U postgres dm3` |
| Объектное хранилище | `bash docker/scripts/restore-storage.sh /var/backups/storage/<каталог>` |

Подключаться к базе `dm3` может только роль `dm_app`. Право у остальных ролей отнимает `docker/postgres-init.sh`, а он работает только на пустом томе. Восстановление в существующую базу или в базу, созданную руками, этого запрета не несет. После восстановления запрет проверяет `bash docker/scripts/check-database-privileges.sh`, а если проверка упала, его возвращает `docker exec dm-pg psql -U postgres -c "REVOKE CONNECT ON DATABASE dm3 FROM PUBLIC"`.

Хранилище восстанавливается ключом `dm-app` командой `cp --recursive`, а не `sync`: `sync` читает список бакета, а права List у ключа приложения нет. Скрипт сверяет `StorageConfigurationShould`.

## Масштабирование

API работает в одном экземпляре, и `container_name` фиксирует это на уровне compose. В процессе API живут периодические задания (чистки, дайджесты, напоминания) без выборов лидера, и второй экземпляр выполнил бы их второй раз, а идемпотентны они не все. Снимается ограничение выносом заданий в свой процесс, как сделано с почтой и уведомлениями, либо распределенной блокировкой.

Realtime-пуш второму экземпляру не мешает: каждый экземпляр слушает канал уведомлений базы своим соединением, и пуш доходит до всех.

## Бэкапы

Ночные задания ставит `docker/scripts/install-cron.sh`: `backup-postgres.sh`, `backup-storage.sh` (ключом `dm-backup`, который только читает и перечисляет) и `verify-backup.sh`, который проверяет возраст, размер и целостность копий. Срок хранения задает `RETENTION_DAYS`, по умолчанию 30 дней.

Ожидающих писем и событий в бэкапе нет. Дамп базы несет структуру таблицы `OutboxEvents` без строк, потому что тело письма лежит там открытым текстом вместе с рабочей ссылкой подтверждения. После восстановления очередь пуста, и письма и события, которые ждали отправки в момент дампа, не уходят. Имя таблицы в шаблоне исключения стоит в двойных кавычках: без них `pg_dump` приводит его к нижнему регистру и не исключает ничего. Исключение на настоящем дампе проверяет `docker/scripts/check-dump-excludes-outbox.sh` в джобе `deployment-smoke`.

Границы хранилища проверяет `docker/scripts/check-storage.sh` в джобе `deployment-smoke`, и новый тег или дайджест SeaweedFS принимается только при ее зеленом прогоне.
