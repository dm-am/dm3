# Требования безопасности DM3

Требования безопасности и записанные исключения из них. Таблицу перечисления аккаунтов в обе стороны держит [IdentifierDisclosureShould](../../test/DM.Architecture.Tests/IdentifierDisclosureShould.cs). Другие правила держат тесты, названные у правила, где теста нет, правило держит ревью.

## Требования к хешированию паролей

Argon2id по рекомендации OWASP: память 19 MiB, две итерации, параллелизм 1,
соль 75 байт (минимум 16), хеш 32 байта. PBKDF2 нужен только ради FIPS-140, а
Argon2id за счет расхода памяти устойчивее к перебору на GPU и ASIC. Параметры
в [HashProvider.cs](../../src/DM.Domain.Account/Features/Security/HashProvider.cs), длина соли в
[SecurityManager.cs](../../src/DM.Domain.Account/Features/Security/SecurityManager.cs).

## Требования к токенам

AES-256-GCM: ключ 32 байта, nonce 12 байт, свой на каждое шифрование, тег 16
байт. Формат и смена ключа в
[AesGcmSymmetricCryptoService.cs](../../src/DM.Domain.Account/Features/Security/AesGcmSymmetricCryptoService.cs).

Ключ шифрования не имеет дефолта в репозитории: им шифруются токен сессии, кука
проверки второго фактора и секрет TOTP в базе, и ключ из исходников дает
подделать сессию любому читателю кода. Без ключа или с ключом не в 32 байта
приложение не стартует. Значение одно на все экземпляры приложения: ссылку
из письма, выданную под одним адресом сайта, открывают по другому, и
расшифровать токен обязана принимающая сторона. Ключ живет только на
экземплярах приложения: точка присутствия кода приложения не выполняет, и
расшифровывать ей нечего.

Значение из письма в базе не хранится: оно открывает сброс пароля, активацию и
смену почты, то есть это учетные данные. Строка держит только SHA-256 от него
без соли (на входе наша случайность, а не пароль человека), и дамп или бэкап не
дает ни одного живого доступа
([ConfirmationSecret.cs](../../src/DM.Domain.Core/Tokens/ConfirmationSecret.cs)).
Приглашение в игру или блог хранится идентификатором: его гасит адресат, уже
вошедший на сайт. Ссылка несет значение во фрагменте, который не уходит на
сервер и не попадает ни в журнал доступа, ни в Referer, а страница сразу стирает
его из адреса
([confirmationToken.ts](../../src/DM.Web.Client/src/shared/lib/utils/confirmationToken.ts)).

## Конвенция конфигурации и секретов

| Что | Где живет |
|-----|-----------|
| Значения по умолчанию для localhost | `appsettings.json`, отслеживается гитом, свежий клон собирается и запускается |
| Настоящие учетные данные любой среды | Переменные `DM_*` или файл в `secrets/`, дефолта в репозитории нет |

Значение, которое хоть в одной среде является секретом, дефолта в репозитории не
имеет, а его отсутствие валит старт. Игнорировать `appsettings.json` целиком не
защита: так воркеры оставались без конфигурации в свежем клоне, а ключ
шифрования все равно лежал в отслеживаемом файле. Какие переменные обязательны и
как их получить, сказано в [CONFIGURATION.md](../references/CONFIGURATION.md).

Ни один сервис не ходит административной учеткой хранилища: утекший администратор
это все хранилище, а не данные одной фичи. Приложение ходит ролью-владельцем
своей базы, экспортер метрик ролью с одними представлениями статистики,
объектное хранилище учеткой одной корзины. Суперпользователь Postgres нужен
только инициализации пустого тома
([postgres-init.sh](../../docker/postgres-init.sh)), поэтому смена учетных
данных ролей требует пересоздания тома. У объектного хранилища администратора
нет вовсе, корзину и учетки при каждом старте выставляет
[storage-start.sh](../../docker/storage-start.sh).

## Защита от атак (чеклист)

| Атака | Требуемая защита |
|-------|------------------|
| Чужой скрипт на странице (XSS) | Кука сессии HttpOnly, CSP |
| CSRF | SameSite=Lax и проверка Origin в CSRF middleware |
| Перебор пароля | Rate limiting, растущая задержка, блокировка после 15 неудач на 30 минут |
| Подбор по времени ответа | Сравнение за постоянное время (`FixedTimeEquals`) |
| Подделка токена | Тег аутентификации AES-GCM |
| Встраивание в чужой фрейм | `X-Frame-Options: DENY` и `frame-ancestors 'none'` |
| Угадывание типа содержимого | `X-Content-Type-Options: nosniff` |
| Обращение к сети читателя из чужого контента | Loopback- и приватные адреса в BBCode-URL не становятся src и href |
| Подмена адреса клиента | X-Forwarded-* обрабатывает только middleware и только для сетей из конфигурации |
| Утечка внутренних деталей | Необработанное исключение отдает постоянный заголовок и токен корреляции, текст только в лог |

SameSite=Lax, а не Strict: Strict не отправляет куку при переходе по ссылке из
письма, и активация со сбросом пароля открывались бы гостем. Lax отдает куку
только навигации верхнего уровня, межсайтовые подзапросы ее не получают.

Читать `X-Forwarded-For` из кода запрещено: заголовок пишет вызывающая сторона,
а прокси лишь дописывает свой пир. Достоверен только `Connection.RemoteIpAddress`
после `UseForwardedHeaders`. По умолчанию доверенных сетей нет, и заголовок не
обрабатывается. Доверенная сеть заполняется только там, где прокси единственный
вход. Если в диапазон попадают обычные клиенты, адрес подделает любой из них, а
у развертывания с напрямую опубликованным портом приложения доверенных сетей нет
вообще.

Проверка адресов в BBCode не защита от SSRF: она бережет loopback и локальную
сеть браузера читателя. Серверный запрос по адресу из пользовательского
контента (превью ссылки, загрузка картинки по URL) проверяется отдельно, после
DNS-резолва и по адресу, с которым реально идет соединение. Имя, резолвящееся в
приватный адрес, на пути рендера не ловится.

## Security Headers (требования)

| Header | Требуемое значение |
|--------|-------------------|
| X-Frame-Options | `DENY` |
| X-Content-Type-Options | `nosniff` |
| Referrer-Policy | `strict-origin-when-cross-origin` |
| Permissions-Policy | `geolocation=(), microphone=(), camera=()` |
| Content-Security-Policy | `default-src 'self'`, `script-src` без `'unsafe-inline'` везде, кроме Development |
| Strict-Transport-Security | `max-age=31536000; includeSubDomains`, только production и не на localhost |

`includeSubDomains` обязывает каждый поддомен отдавать https, точку присутствия
тоже ([POINT_OF_PRESENCE.md](../guides/POINT_OF_PRESENCE.md)).

CSP документа ([nginx.conf](../../src/DM.Web.Client/nginx.conf)) и API
([SecurityHeadersMiddleware.cs](../../src/DM.Web.API/Middleware/SecurityHeadersMiddleware.cs))
делают два допущения. `style-src 'unsafe-inline'` нужен стилям, которые
вставляют Vue и редактор TipTap. `img-src` открыт для `https:` и `data:`
(документ еще для `http:` и `blob:`): картинки идут с адреса imgproxy или CDN из
настроек развертывания и из BBCode откуда угодно, `data:` это аватар по
умолчанию, `blob:` сжатие картинки в Safari. Строгим остается `script-src`:
встроенные скрипты документа названы sha256 тела, и
[csp.spec.ts](../../src/DM.Web.Client/src/csp.spec.ts) пересчитывает их из
index.html. `connect-src 'self'` предполагает клиент, API и хаб на одном
происхождении, API на другом адресе вписывается сюда.

Заголовки нужны и ответам API, и HTML-документу: `frame-ancestors` и
`script-src` действуют там, где живет документ. Одну политику выставляет ровно
один слой, а слой перед ним снимает пришедшую снизу через `proxy_hide_header`:
`add_header` не заменяет заголовок, а добавляет второй, и когда значения
разойдутся, победителя выберет разбор заголовка, а не автор правки. Край
([edge-locations.conf](../../docker/nginx/edge-locations.conf)) ставит четыре
заголовка и снимает их копии у API, CSP ставят только API и контейнер клиента.

## Чеклист для новых ручек

- Rate limiting на ручке аутентификации и на гостевой ручке аккаунта.
- Валидация входа через FluentValidation.
- Пользовательский текст уходит наружу только через серверный рендер BBCode.
- `[AuthenticationRequired]` на всякой ручке, которая действует или читает от имени вошедшего пользователя.
- Одинаковый ответ на существующего и несуществующего пользователя, либо строка в таблице исключений ниже.
- Запись событий безопасности в журнал.

## Записанное исключение: перечисление аккаунтов

Семь ручек отвечают на вопрос "занят ли этот адрес" или "занято ли это
имя", и это осознанный компромисс, а не недосмотр:

| Ручка | Что раскрывает | Зачем |
|-------|----------------|-------|
| `POST /v1/account/check-email` | почта занята, свободна или ждет активации | форма регистрации обязана сказать, что адрес занят |
| `POST /v1/account/check-username` | имя занято (одна причина: живое имя, имя удаленного аккаунта и прежнее имя не отличаются) | то же для имени |
| `POST /v1/account/register` | почта занята (живым или удаленным аккаунтом, без различия) | запасной выход того же поля, когда проверка на первом шаге промолчала или проиграла гонку |
| `POST /v1/account/activation` | имя занято, только держателю действующей ссылки | форма выбора имени обязана предложить выбрать другое |
| `POST /v1/account/email-change` | почта занята, только владельцу сессии после верного пароля (живой и удаленный не отличаются) | форма смены адреса обязана сказать, что адрес не подойдет, до письма |
| `POST /v1/account/recovery` | аккаунта нет, выслан сброс или выслана активация, удаленный аккаунт отвечает как живой | форма восстановления обязана отличать опечатку в адресе от отправленного письма |
| `POST /v1/account/login` | регистрация по адресу начата и не завершена | пользователю, чье письмо активации потерялось, нужен путь к повторной отправке, а не "неверная почта или пароль" |

### Почему не закрываем

Закрыть можно только все сразу. Пока проверка занятости отвечает при
регистрации, схлопнутый ответ восстановления перечисление не убирает, а только
лишает пользователя сообщения об опечатке. Полное закрытие значит регистрацию,
которая не объясняет, почему не проходит. Для сайта с публичными профилями цена
по удобству выше пользы от скрытия факта, который и так виден.

### Что обязательно взамен

Rate limiting на всех семи (он замедляет перечисление, но не предотвращает, и
защитой его не называть) и запись каждого раскрывающего ответа в лог: событие,
адрес клиента, исход. Сам идентификатор в лог не пишется, иначе месячные логи в
Grafana стали бы списком чужих адресов и имен. Счет по значениям, если
понадобится, берется от HMAC идентификатора.

### Что остается закрытым

Гость получает об адресе или имени один бит, свободен или занят, а для адреса
еще "ждет активации" (заявка без аккаунта). Удаление и бан называются только
после доказанного пароля, бан с датой окончания, и тогда же отказ пишется в
журнал безопасности аккаунта. До пароля неверный пароль, отсутствующий,
удаленный и забаненный аккаунт дают один ответ, побайтово и за то же время.

Удаленный аккаунт на гостевой ручке отвечает как живой: проверка
занятости и регистрация говорят "занят", восстановление отдает ту же квитанцию
и письма не шлет. Слова "удален" гость не получает ни на экране, ни в ящике, и в
таблицу это состояние не вносится: пока одна ручка говорила "не найден", а
другая "занят", удаление вычислялось вычитанием двух ответов. Дорога назад одна,
обращение в поддержку с причиной "Восстановление удаленного аккаунта". Карточка
входа предлагает его на месте "Не могу войти" только после доказанного пароля,
когда сервер уже назвал аккаунт удаленным, так что ссылка ничего нового не
раскрывает.

Незавершенная регистрация раскрывается и до пароля, хотя пароль у заявки есть:
тот же факт уже отдают проверка занятости и восстановление, а ответ нужен тому,
у кого потерялось письмо.

Страница по ссылке из письма говорит о ссылке и действии читателя, а не о
состоянии аккаунта: удаленный аккаунт на ней отвечает как погашенная ссылка.
Состояние, без которого действие не объяснить ("адрес уже занят другим
аккаунтом", "защита не включена"), и адрес, на который ушло письмо,
произносятся: входом служит секрет из письма. Ссылка отмены отложенного
отключения второго фактора гаснет вместе с отключением и не говорит "уже
отменено" про защиту, которой нет.

Имя публично по замыслу. Проверка имени отвечает "занято" и не отличает живое
имя от зарезервированного за прежним владельцем, а связка "занято, а профиля
нет" остаточно выдает, что кто-то ушел: это принятая цена резервирования имен
под старыми постами. Наличие второго фактора не раскрывает никакая ручка,
запрос отключения отвечает одной квитанцией любому адресу.

## Написанное удаленными аккаунтами

Все, что удаленный аккаунт написал, остается на месте. Чтения содержимого
снимают фильтр аккаунтов и только его, а удаленный автор, мастер или редактор
приходит через общую проекцию пользователя пустым (null, без имени, адреса,
аватара и идентификатора), и клиент подписывает его "Аккаунт удален". Списки
людей в том же ответе (ассистенты игры и блога, модераторы раздела) удаленных не
показывают, фильтры по имени их старое имя не находят. Что снимает фильтр, держит
[RemovedAuthorRowsShould](../../test/DM.Architecture.Tests/RemovedAuthorRowsShould.cs).

Профиль `/users/Аккаунт удален` ничьей строкой не является и раскрывает только
суммы публичных счетчиков всех удаленных: рейтинг, число постов, оцененных
постов, игр и блогов. Кто они, сколько их и когда ушли, наружу не уходит. Строки
удаленных читаются мимо фильтра отдельным запросом, никогда подзапросом внутри
списка, потому что снятие фильтра действует на весь запрос, а сам список
читается с фильтрами доступа читателя, и закрытое остается закрытым. Сводка
одна на всех читателей и кэшируется. Кто знает это имя, держит
[RemovedAccountReachShould](../../test/DM.Architecture.Tests/RemovedAccountReachShould.cs),
остальные ручки отвечают на него как на неизвестное имя, а резерв имени
отвечает "занято", как любое занятое имя
([USERNAME_POLICY.md](USERNAME_POLICY.md#зарезервированные-имена)).

## Требования к паролям

От 8 до 128 символов, правил состава нет (NIST SP 800-63B-4), значения в
[PasswordPolicyConfiguration.cs](../../src/DM.Domain.Account/Configuration/PasswordPolicyConfiguration.cs).
Пароль сверяется с утечками HaveIBeenPwned через k-anonymity: наружу уходят
первые пять знаков SHA-1. Короткий пароль клиент называет слабым, шкала
заполняется к 15 символам. Запрета на повтор прежних паролей нет.

Журнал безопасности аккаунта и сессия хранят IP и User-Agent, журнал открыт
владельцу через API. Сроки сессий записаны в
[AUTHENTICATION.md](../architecture/AUTHENTICATION.md#сессии). Второй фактор
(TOTP и резервные коды) не обязателен ни одной роли, а включенный требуется от
учетки любой роли
([AUTHENTICATION.md](../architecture/AUTHENTICATION.md#двухфакторная-аутентификация)).

## Конфиденциальность пользовательского контента (BBCode)

Контракт целиком в [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md):
`[private]` фильтруется на сервере до сериализации JSON, вырезание не оставляет
следа, модератор приватного текста не видит, разметка разбирается один раз и
кодируется по месту записи, а сохранение отвергает `[private]` с названной
причиной вместо молчаливого стирания. Здесь только правила, которых там нет.

Аудитория `author_edit` выдается только автору контента, и авторство сверяется
при рендере, а не на ручке: заголовок аудитории клиентский и применяется ко
всему ответу, а ответ несет контент разных авторов. Незаполненный идентификатор
автора значит "не автор".

Подстрока, вырезаемая до разбора, не может нести разметку `[private]`, иначе
тег не вырезается и уходит в разбор: проход, вырезавший тег до разбора, уже
уносил текст, который разбор должен был увидеть, и фильтру видимости нечего
было скрывать. Серверное регулярное выражение над недоверенным вводом
исполняется без возвратов либо с ограничением времени.

Текст внутри `[private]` не появляется ни в одном выводе для того, кто не вправе
его читать. Проверяется это на сгенерированных входах с уникальным каждым
словом: слово закрытого блока не встречается ни в HTML, ни в текстовом виде, ни
в поисковой проекции
([TESTING.md](../guides/TESTING.md#генеративные-проверки-разметки)). Счет
токенов и узлов только вторая проверка, он не видит, куда легло содержимое
узла, и берется над текстом пути сохранения до любых преобразований.

Имена тегов и параметров сравниваются без учета регистра только по латинским
A-Z, кодами ASCII. Средства языка складывают буквы по-разному: .NET с
`IgnoreCase` и `ToLowerInvariant` считают знак Кельвина (U+212A) буквой `k`,
клиентское `/i` без флага `u` не считает. Тогда `[lin`, U+212A, `]` одной
стороне ссылка, а другой текст, и из такого расхождения уже приходили хранимый
XSS и утечка приватного текста. Буква другого алфавита делает имя словом в
прозе, исключений нет и у `[private]`.

### Путь сохранения читает тот же текст, что и разбор

Разбор до чтения убирает управляющие символы, кроме табуляции и переводов
строки, и символы, переворачивающие видимый порядок текста (U+202A..U+202E,
U+2066..U+2069). Удаление склеивает то, что стояло по краям, и склейка бывает
тегом: `[m`, U+0001, `od]` для санитайзера не маркер, а на странице блок
модератора, и `[nopa`, U+0001, `rse]` для проверки `[private]` не пример, а на
странице пример, печатающий приватный текст всей комнате. Поэтому санитайзер
привилегированной разметки и проверки `[private]` читают текст после того же
удаления. Правило записано дважды, в разборе и в
[ParserInput.cs](../../src/DM.Domain.Core/Content/ParserInput.cs), потому что
доменная сборка парсер не видит, и
[ControlCharacterMarkupShould](../../test/DM.Infrastructure.Core.Tests/ControlCharacterMarkupShould.cs)
держит оба места вместе на каждом управляющем, пробельном, служебном и
суррогатном символе в каждом месте тега.
