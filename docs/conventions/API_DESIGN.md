# API Design

Контракт HTTP API: адреса, ответы и ошибки, коды, параметры списков, лимиты, заголовки, кеширование и realtime. Сам документ читают два теста: RateLimitPipelineShould раздел о лимитах, OpenApiContractShould примеры адресов. Правило, которое держит тест, называет его рядом с собой, правило без теста держит ревью.

Полный перечень эндпоинтов в Swagger UI, при запуске из исходников это http://localhost:5000/. В production Swagger не отдается.

## Базовая информация

API отвечает с того же origin, что и сайт. Формат JSON в UTF-8, вход по HttpOnly-куке сессии ([AUTHENTICATION.md](../architecture/AUTHENTICATION.md)).

**`v1` это фиксированный префикс, а не схема версионирования.** Единственный потребитель живет в том же репозитории, и ломающее изменение вносится вместе с правкой клиента одним коммитом, поэтому `Asp.Versioning` не заводится. Пересмотр, когда появится внешний потребитель, который обновляется не вместе с нами.

**Контракт выпускает сборка.** OpenApiContractShould пишет по документу Swagger на группу (`GroupName` контроллера) в `artifacts/openapi/`, CI выкладывает их артефактом `openapi-contract`, в репозиторий они не коммитятся: закоммиченная копия расходится с кодом молча. Тот же прогон сводит контракт к слепкам, которые коммитятся намеренно, правятся прогоном, а тест падает, пока новая версия не закоммичена, так что изменение API видно в ревью строкой диффа.

| Слепок | Что в нем | Кто еще его читает |
|---|---|---|
| `artifacts/openapi-contract.json` | имена свойств каждой схемы | `contract.spec.ts`, модели клиента |
| `artifacts/openapi-routes.json` | каждый метод с путем | `routes.spec.ts`, адреса вызовов клиента |
| `artifacts/openapi-public-routes.json` | операции, открытые гостю | ревью |

## Три типа endpoints

| Тип | Обычные глаголы | Глагол в пути | Пример |
|-----|-----------------|---------------|--------|
| Resource | GET, POST, PUT, PATCH, DELETE | нет | `/v1/users/{username}` |
| Query | GET | допустим | `/v1/users/me/subscriptions/check` |
| Action | POST | допустим | `/v1/account/login`, `/v1/global-chat/events/{id}/join` |

Глаголы обычные для типа, а не белый список. Записанное исключение: проверки занятости логина и почты (`/v1/account/check-username`, `/v1/account/check-email`) идут POST, чтобы идентификатор не попадал в URL и в логи.

### PUT или PATCH

**PUT это полная замена ресурса, PATCH частичное слияние.** После PUT ресурс равен телу, и чего в теле нет, того у ресурса не остается. Тело PATCH несет только изменяемые поля, отсутствующее поле и `null` там значат "не трогать", поэтому обнулить поле PATCH нельзя, для этого есть полная замена или отдельная операция. Запрос, назвавший часть ресурса и оставивший остальное, это PATCH, как бы операция ни называлась.

- **Переупорядочивание это PUT.** Ресурс здесь порядок элементов внутри родителя, и тело обязано назвать все элементы по одному разу. Неполный список отвергается как невалидный, иначе неназванный элемент остался бы на позиции, отданной другому.
- **Upsert по естественному ключу это PUT.** Адрес известен до создания записи (`PUT /v1/users/me/notes/{username}`), первый вызов создает, повторный заменяет.

Одинаковые по смыслу операции носят один глагол, иначе читатель ищет разницу в семантике, которой нет.

## Форматы ответов

| Тип ответа | Формат |
|------------|--------|
| Одиночный ресурс | `Envelope<T>`, поле `resource` |
| Коллекция | `ListEnvelope<T>`, поля `resources` и `paging` (`skip`, `take`, `total`) |
| Курсорная страница | `CursorEnvelope<T>`, `paging` с курсорами `nextCursor` и `prevCursor` |
| Ошибка | `ProblemDetails` по RFC 9457, у ошибки валидации еще `errors` по полям |

Типы конвертов лежат в `src/DM.Web.API/Shared/Dto/`, форму на проводе держит ResponseEnvelopeShould.

**`Envelope<T>` - стандарт для всех одиночных ресурсов.** DTO без конверта считается унаследованным и при доработке приводится к конверту, такие ответы пересчитывает EnvelopeCoverageShould.

**Непосчитанное поле в ответ не кладется.** Схема, вложенная в чужой ответ, часто заполнена только базовой проекцией, и ноль на месте непосчитанного неотличим от настоящего: экран покажет "нарушений: 0" про того, у кого их десять. Поэтому агрегат, который считается отдельным запросом, объявляется обнуляемым и опускается при сериализации, а присутствие поля значит "посчитано". Второй схемы ради этого не заводят.

**Тип содержимого один.** Успешное тело `application/json`, отказ `application/problem+json`, и контракт называет у ответа ровно один тип: клиент, собранный по документу, выбирает десериализатор по имени типа. Держит OpenApiContractShould.

**Машиночитаемого кода ошибки нет.** Тип отказа несет HTTP-статус, сообщение лежит в `title`, поле `code` не заводится. Значение сверх фразы (дата окончания бана, секунды ожидания) едет расширением problem-документа из `HttpException.Extensions`, и экран произносит его своими словами в своем часовом поясе. Сообщение необработанного исключения клиенту не уходит: 500 отдает постоянный заголовок и токен корреляции.

**`title` это строка интерфейса.** Он показывается читателю как есть, поэтому пишется по-русски по правилам подписей. Отказ из нескольких мест берет формулировку из `RefusalMessage`. Держит RefusalCopyShould.

**Тело ошибки собирает только middleware** из брошенного `HttpException`, контроллер своего не собирает. `[ProducesResponseType]` для статуса от 400 объявляет `ProblemDetails` либо `ValidationProblemDetails`. Держат ErrorBodyOwnershipShould и OpenApiContractShould.

## Коды ответов

| Код | Когда использовать |
|-----|-------------------|
| 200 | Успешный запрос |
| 201 | Ресурс создан (POST) |
| 204 | Успешно, без тела (DELETE, actions) |
| 400 | Невалидные параметры |
| 401 | Требуется аутентификация |
| 403 | Недостаточно прав |
| 404 | Ресурс не найден: нет и не было |
| 409 | Конфликт состояния |
| 410 | Ресурс был и удален, токен или приглашение истекли |
| 429 | Rate limit превышен |

**404 против 410.** Неизвестный идентификатор или имя отвечает `404`, даже когда запись скрыта мягким удалением. `410` требует отдельной проверки, что строка существует, и заводится осознанно: удаленный топик форума, просроченный одноразовый токен из письма, истекшее окно настройки второго фактора, истекшее приглашение. Внутри одного ресурса код один: если чтение отвечает `404` на ненайденный комментарий, правка и удаление отвечают так же.

**Отметка прочитанного это `DELETE` подресурса `unread`**, для элемента (`/v1/chats/{id}/messages/unread`) и для коллекции (`/v1/forum/comments/unread`). Операция идемпотентна и обходится без глагола в пути, второе имя `POST mark-read` не заводится.

**DELETE отвечает `204 No Content` без тела.** Записанное исключение: `DELETE /v1/polls/{id}/vote` отвечает `200` с обновленным `Envelope<Poll>`, чтобы клиент перерисовал результаты без повторного запроса.

**Секрет никогда не едет в пути URL.** Путь пишется дословно в журнал прокси, в лог и в трейс, и ротация секрета превращается в чистку логов. У интеграции берется ее собственное соглашение: Telegram шлет секрет в заголовке, он сравнивается за постоянное время, Discord подписывает каждый запрос, и коды отказа у них те, что требует сама интеграция (`WebhookController`). Незаданный секрет или ключ закрывает эндпоинт.

**Одноразовый токен из письма тоже секрет.** Где владение токеном и есть право на вызов (активация, сброс пароля, смена почты и логина, гостевое обращение), токен едет в заголовке `X-Dm-Account-Token`, у гостевого обращения в `X-Dm-Ticket-Token`, один и тот же у проверки статуса и у завершающего вызова. Ссылка в письме ведет на страницу клиента, а он перекладывает токен в заголовок (сама ссылка описана в [URL_STRUCTURE.md](URL_STRUCTURE.md), раздел "Token"). Отсутствующий, испорченный и неизвестный токен отвечают одинаково. Держит TokenGatedActionsShould.

**`CancellationToken` принимают только GET-экшены.** Многошаговая запись по умолчанию не атомарна, и отмена на середине оставила бы, например, погашенное приглашение действительным. Держит MutatingActionsShould. Разрыв соединения клиентом не ошибка, `ErrorHandlingMiddleware` пишет его отдельной веткой, а не уровнем Critical.

**Заголовок `Location` у 201** указывает на созданный ресурс и ни на что другое. Если своего адреса у подресурса нет, заголовок не ставится (`[CreatedWithoutLocation]`): `Location` на коллекцию отдаст клиенту весь список вместо записи. Завести адрес элемента или не ставить заголовок, решает то, нужен ли этот адрес кому-то кроме заголовка. Держит CreatedLocationShould.

## Pagination, Filtering & Sorting

Один списочный эндпоинт с параметрами вместо отдельных адресов вроде `/games/popular` и `/games/owned`: у `/v1/games` это `sortBy=popularity` и `participating=true`. Авторизация списка тогда одна, а кеш ключуется по URL.

### Pagination

| Тип | Параметры | Использование |
|-----|-----------|---------------|
| Offset | `?skip=20&take=10` | Списки с известным total |
| Cursor | `?cursor=abc&limit=50` | Бесконечная лента |

**Границы страницы.** `take` от 1 до `PagingPolicy.MaxPageSize`, `skip` неотрицателен. Значение вне границ это ошибка валидации, а не урезанная страница, которую клиент примет за полный набор. Верхняя граница обязательна у каждого списка, без нее список становится выгрузкой таблицы. Держит PageSizeLimitsShould.

**Порядок страницы разрешает ничью.** Сортировка по полю с повторами (метка времени, число, название) режется на страницы недетерминированно: запись приходит дважды или пропадает. Поэтому за основным ключом стоит второй, уникальный в наборе, в ту же сторону, и это проверяется тестом на записях с равным ключом через границу страницы. Импорт прежнего сайта приносит такие записи пачками.

Номер страницы в адресной строке сайта другой слой, он в [URL_STRUCTURE.md](URL_STRUCTURE.md), раздел "Пагинация".

### Filtering

```
GET /v1/games?statuses=Active,Draft&hostUsernames=ivan&requiredTags=42
GET /v1/posts?gameId=abc&authorUsernames=ivan
GET /v1/users?role=moderator&isOnline=true
```

Список значений идет через запятую или повтором параметра, флаг булевым значением (`participating=true`), диапазон парой границ (`minRating`, `maxRating`).

**Фильтр, которому ничего не соответствует, дает пустую страницу**, 200 и ноль записей, а не 404: 404 остается за ресурсом, которого нет по адресу. Опечатка в ссылке тогда неотличима от пустой истории, поэтому экран рядом с пустым состоянием показывает, о ком или о чем речь.

### Словарь query-параметров

Одна задача называется одним именем на всех эндпоинтах. Неизвестный параметр молча игнорируется, и имя, неверно угаданное по соседнему списку, возвращает `200` и полный список вместо отфильтрованного.

| Задача | Имя | Не писать |
|--------|-----|-----------|
| Свободный текстовый фильтр | `search` | `q`, `query`, `filter`, `text` |
| Страница по смещению | `skip` + `take` | `number` + `size`, `page`, `offset`, `pageSize` |
| Страница по курсору | `cursor` + `limit` | `after`, `nextCursor`, `count` |
| Граница даты | `<поле>FromUtc` / `<поле>ToUtc` | `<поле>After`/`Before`, голые `after`/`before` |
| Сортировка | `sortBy` + `sortOrder` | `sort`, `order`, `orderBy` |
| Логин пользователя | `username` / `authorUsername` | `user`, `login`, `author` |
| Статус модуля | `statuses` | `status` |
| Статус премодерации | `premoderationStatuses` | `premoderationStatus` |
| Кто ведет игру или блог | `hostUsernames` | `authorUsernames`, `masterUsernames` |

"Кто ведет" и "кто написал" разные фильтры, поэтому мастер игры не `authorUsername`.

**Число имени равно числу значений.** Повторяемый параметр во множественном числе (`statuses`, `authorUsernames`), одиночный в единственном (`status`, `role`). Одно имя с двумя кодировками самая дорогая ошибка: имя скопировано у соседа верно, а значение читается иначе.

**Курсор не синоним смещения.** `cursor` и `limit` только у списков с keyset-обходом (чаты, глобальный чат, поиск сообщений), у остальных `skip` и `take`, номер страницы в смещение переводит клиент.

**`search` на списке не полнотекстовый поиск**, а подстрока без морфологии и ранга, местами с триграммной нечеткостью. Морфология, ранжирование и сниппет только под `/v1/search/*`.

Держит QueryVocabularyShould, читая имена `[FromQuery]`-параметров из сборки API.

### Sorting

```
GET /v1/games?sortBy=popularity&sortOrder=desc
GET /v1/posts?sortBy=rating&sortOrder=desc&take=1
```

Формат `?sortBy=<поле>&sortOrder=asc|desc`. Общего направления по умолчанию нет, клиент, которому важен порядок, передает `sortOrder` явно.

**Допустимые поля перечислены не здесь, а в таблице `SortVocabulary` по типу запроса.** Из нее фильтр действия отвечает 400 на чужое поле, и из нее же поля публикуются в контракт. Список без записи там роняет OpenApiContractShould.

**Неизвестное поле или направление это ошибка валидации**, а не молча порядок по умолчанию. Держит SortVocabularyShould.

### Когда отдельный endpoint оправдан

1. Действие: `/v1/account/login`, `/v1/global-chat/events/{id}/join`.
2. Агрегация: `/v1/stats`, `/v1/leaderboards/{year}`.
3. Семантический шорткат, когда адрес называет устойчивое понятие ("лучшая публикация", "активный бан"), а не комбинацию фильтров. Перечня таких адресов нет намеренно, решает ревью по этому критерию.

## Rate Limiting

| Эндпоинты | Лимит |
|-----------|-------|
| Глобальный | 300 req/min |
| Аутентификация | 5 req/min |
| Username check | 20 req/min |
| Email check | 10 req/min |
| Настройки двухфакторной аутентификации | 10 req/min |
| Загрузка файлов | 10 req/min |
| Дорогие чтения | 30 req/min, скользящее окно |
| Личные разделы аккаунта и обычные записи | 60 req/min |

Источник чисел `RateLimitingExtensions`.

Счет ведется по аккаунту там, где запрос его несет, и по адресу иначе: гости за общим адресом делят бюджет, вошедшие нет. Глобальный лимит, аутентификация и проверки занятости логина и почты всегда по адресу, аккаунта у такого запроса еще нет. Бюджет выбирается по тому, чем запрос удостоверен, а не по функции, поэтому анонимные эндпоинты контроллера могут стоять на адресном бюджете, а эндпоинты с сессией на бюджете аккаунта. Строгий адресный бюджет на эндпоинте с сессией за общим адресом отвечает 429 первому же честному пользователю.

При `RateLimiting:Enabled=false` политики регистрируются как no-op, эндпоинт, просящий политику по имени, поднимается одинаково. Превышение отвечает `429 Too Many Requests` с `Retry-After`.

## Кросс-доменные заголовки

При запуске из исходников сайт и API разъезжаются по портам, и браузер спрашивает разрешение до запроса. Оба перечня разрешения в `Startup.cs` ведутся руками и закреплены тестом CorsPolicyShould: обратный прокси на один адрес прячет их ошибки до дня, когда адреса разъедутся.

- **Новый заголовок запроса вводится той же правкой, что и строка в `WithHeaders`.** Без нее preflight отвечает без заголовка, и браузер отменяет запрос целиком.
- **Заголовок ответа, который клиент читает, объявляется в `WithExposedHeaders`** (`Location` у `201`, `Retry-After` у `429`). Необъявленный для кода страницы равнозначен отсутствующему.

## Кеширование ответов

`Cache-Control: public` только для ответа, одинакового для всех: анонимного, любого пользователя и любого `X-Dm-Audience`. Одно персональное поле (счетчик непрочитанного, признак "мое") делает ответ `private`: кеш и прокси без `Vary` ключуются по методу и пути и отдадут данные первого запросившего всем.

**Личное `private`, общее `public` плюс явный `Vary` на каждый заголовок, от которого ответ зависит.** Держат PubliclyCacheableActionsShould и PublicCacheableResponsesShould.

## Realtime (SignalR)

Хаб `/hubs/notifications`, транспорт согласует SignalR, вход по той же HttpOnly-куке сессии, клиент в `src/DM.Web.Client/src/shared/api/client.ts`.

- Хаб только отдает, клиент его методов не вызывает.
- Соединения учитываются в памяти процесса по connection ID, без групп, карта пользователя перестраивается на каждом подключении, переприсоединять после разрыва нечего.
- Гость подключается и получает только широковещательные события (глобальный чат и его эвенты), адресные уходят вошедшим.
- Токен в query-строке не принимается: URL попадает в логи прокси.
- Формат тот же, что у REST (`eventType` строкой, `payload` в camelCase), пуш и строку списка уведомлений собирает один маппер, пуш всегда непрочитан.

**Пуш это намек, истина в REST.** Хаб не хранит очереди, события за разрыв потеряны, доставка от outbox до хаба допускает пропуск и повтор, номера последовательности нет. Поэтому для всех событий:

- на событие потребитель перечитывает состояние запросом, а не применяет `payload`, тогда повтор и перестановка безвредны
- на переподключение и на возврат вкладки на экран состояние перечитывается заново
- клиент переподключается сам, бесконечно и с растущей задержкой, первое подключение тоже
- пуш, годный только как событие (анимация, звук, "идет сейчас"), не перечитывается

Живой список на событие о новом элементе дочитывает хвост с дедупликацией по идентификатору, а если хвост не пересекается с показанным, перечитывается целиком, иначе между старым и новым остается дыра.

## Заголовок X-Dm-Audience

Поля с пользовательским BBCode сервер рендерит под намерение из `X-Dm-Audience`. Без заголовка и при неизвестном значении это `display`, `author_edit` получает только автор контента, остальным отдается `display`. Значения и видимость тегов при каждом в [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md), раздел "Audience".
