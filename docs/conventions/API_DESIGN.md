# API Design — DM3

> **User Story:** "Какие принципы API? Какие форматы ответов?"

> **SSOT:** Полный список endpoint'ов — в Swagger: http://localhost:5000/

---

## Базовая информация

| Параметр | Значение |
|----------|----------|
| Base URL | Тот же origin, что и у сайта: отдельного адреса у API нет. При запуске из исходников — `http://localhost:5000` |
| API Version | v1 |
| Формат | JSON, UTF-8 |
| Аутентификация | HttpOnly Cookie (BFF Pattern) |

**`v1` — фиксированный префикс, а не схема версионирования.** У API один
потребитель, живущий в том же репозитории, поэтому согласования версий,
per-endpoint устаревания и параллельной жизни двух версий нет и не
предполагается: ломающее изменение вносится вместе с правкой клиента в одном
коммите. Заводить `Asp.Versioning` ради этого значит принести машинерию под
сценарий, которого не будет. Триггер пересмотра — первый внешний потребитель,
который обновляется не вместе с нами.

**Контракт выпускается артефактом сборки.** Swagger не отдается в production, и
до появления артефакта единственная машиночитаемая копия контракта жила внутри
запущенного Development-контейнера — сверить с ней было нечего, чем и объясняются
эндпоинты, обещавшие одну форму ответа и клавшие на провод другую.
Интеграционный набор пишет девять групповых документов в `artifacts/openapi/`,
CI выкладывает их как `openapi-contract`. В репозиторий они не коммитятся:
закоммиченная копия расходится с кодом молча.

**Слепок контракта — вторая половина того же механизма.** Тот же прогон сводит
опубликованные схемы к перечню имен свойств и кладет результат в
`artifacts/openapi-contract.json`, и этот файл коммитится намеренно: по нему тест
клиента сверяет написанные вручную модели с серверными, а изменение схемы видно в
ревью строкой диффа. Деление такое: полные документы — артефакт сборки, сведенный
слепок — в репозитории, и правится он прогоном, а не руками.

## Философия

> **Подход:** Pragmatic REST (Stripe, GitHub)

1. **Понятность > Догма** — читаемые URL важнее REST-пуризма
2. **Консистентность** — одинаковые паттерны везде
3. **Предсказуемость** — ожидаемое поведение
4. **Простота** — минимум сложности

## Три типа endpoints

| Тип | HTTP | Глаголы в URL | Пример |
|-----|------|---------------|--------|
| **Resource** | GET/POST/PUT/PATCH/DELETE | Нет | `/users/{id}` |
| **Query** | GET | Допустимы | `/account/check-email` |
| **Action** | POST | Допустимы | `/account/login`, `/games/{id}/join` |

Колонка "HTTP" называет глаголы, обычные для эндпоинта такого типа, а не белый
список. Какой из двух пишущих глаголов брать, решает критерий ниже.

### PUT или PATCH

**PUT — полная замена ресурса, PATCH — частичное слияние.** Тело PUT задает
состояние целиком: после вызова ресурс равен присланному телу, и того, чего в
теле нет, у него не остается. Тело PATCH несет только изменяемые поля.
Отсутствующее поле и присланный `null` означают там одно и то же "не трогать",
поэтому обнулить поле частичной правкой нельзя: для этого берется полная замена
либо отдельная операция.

Отсюда обязанность, про которую забывают чаще всего: у PUT тело определяет
судьбу всего, что входит в ресурс. Пока запрос, назвавший часть ресурса,
оставляет остальное как было, это слияние, и глагол ему PATCH, как бы операция
ни называлась.

Два случая, в которых глагол выбирают неверно чаще всего:

- **Переупорядочивание.** Ресурс тут это порядок элементов внутри родителя, а
  тело несет его целиком: позиция элемента есть его место в присланном списке.
  Значит PUT, и значит тело обязано назвать все элементы родителя, каждый по
  одному разу. Неполный список оставил бы неназванным элементам позиции,
  которые запрос только что раздал другим: два элемента на одном месте и один
  сдвинутый запросом, который его не упоминал. Такое тело отвергается как
  невалидное, а не домысливается сервером.
- **Upsert по естественному ключу.** Адрес известен вызывающему до создания
  записи (`.../{username}`), тело задает ее целиком: первый вызов создает,
  повторный заменяет. Тоже PUT.

Одинаковые по смыслу операции носят один глагол. Два эндпоинта, меняющие
порядок элементов, не могут быть один PUT, а другой PATCH: читатель второго
решит, что разница в глаголе означает разницу в семантике, и станет ее искать.

## Форматы ответов

| Тип ответа | Формат |
|------------|--------|
| Одиночный ресурс | `Envelope<T>` с полем `resource` |
| Коллекция | `ListEnvelope<T>` с `paging` |
| Курсорная пагинация | `CursorEnvelope<T>` с `cursor` |
| Ошибка | RFC 9457 `ProblemDetails` |

```json
// Одиночный ресурс — Envelope
{ "resource": { "id": "...", "username": "john" } }

// Коллекция — ListEnvelope
{ "resources": [...], "paging": { "skip": 0, "take": 20, "total": 150 } }

// Ошибка — ProblemDetails, Content-Type: application/problem+json
{ "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Блог не найден", "status": 404, "traceId": "00-..." }

// Ошибка валидации — то же плюс errors по полям
{ "title": "Некорректные данные", "status": 400,
  "errors": { "AcceptedRules": ["Необходимо принять правила сайта"] } }
```

> **Правило:** `Envelope<T>` — стандарт для всех одиночных ресурсов.
> Endpoint'ы, возвращающие DTO без конверта, — legacy; при доработке приводить к `Envelope<T>`.

> **О неполных проекциях.** Одна схема нередко едет в двух полнотах: запрошенная
> по имени, она посчитана целиком, а вложенная в чужой ответ — заполнена только
> тем, что дает базовая проекция. Поле, которого никто не считал, в ответ не
> кладется вовсе. Иначе ноль и пустой список неотличимы от посчитанных, и
> потребитель показывает "нарушений: 0" про того, у кого их десять.
>
> Отсюда правило: агрегат, который заполняется отдельным запросом, объявляется
> обнуляемым и опускается при сериализации, а наличие поля в ответе означает
> "это значение посчитали". Дискриминатор — само присутствие поля; заводить
> вторую схему под ту же сущность ради этого не нужно.

> **О типе содержимого.** Тело успешного ответа — `application/json`, тело
> отказа — `application/problem+json`. Других типов у ответов нет, и
> опубликованный контракт обязан называть ровно один: клиент выбирает
> десериализатор по имени типа, а не по статусу.

> **Об ошибках.** Машиночитаемого кода ошибки в контракте нет: тип ошибки несет
> HTTP-статус, человекочитаемое сообщение лежит в `title`. Заводить поле `code` не
> нужно — нужно, чтобы статус был выбран правильно. Сообщение необработанного
> исключения клиенту не уходит никогда: 500 отдает постоянный заголовок и токен
> корреляции для поиска в логах.
>
> Сообщение отказа — это строка интерфейса, а не заметка для разработчика: `title`
> показывается читателю как есть, без расшифровки на клиенте. Отсюда язык:
> сообщение пишется на языке интерфейса и подчиняется тем же правилам русского
> текста, что и подпись под полем. Повторяющийся отказ берет формулировку из
> общего словаря: один отказ формулируется один раз, иначе два ответа на одну
> причину расходятся в словах.
>
> Ответ с ошибкой формирует только middleware, из брошенного `HttpException`.
> Собирать тело ошибки в контроллере нельзя: получится форма, которой нет ни у
> одного другого ответа. Соответственно `[ProducesResponseType]` для любого
> статуса от 400 объявляет `ProblemDetails` либо `ValidationProblemDetails` —
> это проверяет интеграционный тест по опубликованному документу.
>
> Тип содержимого ответа с ошибкой — `application/problem+json`, успешного ответа
> с телом — `application/json`, и в опубликованном документе у ответа объявлен
> ровно один тип. Перечислять типы, под которыми ответ не отдается, нельзя:
> клиент, собранный по документу, ищет десериализатор по имени типа и для
> незаявленного получает нетипизированный поток.

## Коды ответов

| Код | Когда использовать |
|-----|-------------------|
| 200 | Успешный запрос |
| 201 | Ресурс создан (POST) |
| 204 | Успешно, без тела (DELETE, actions) |
| 400 | Невалидные параметры |
| 401 | Требуется аутентификация |
| 403 | Недостаточно прав |
| 404 | Ресурс не найден: нет и не было |
| 409 | Конфликт состояния |
| 410 | Ресурс был и удален, токен или приглашение истекли |
| 429 | Rate limit превышен |

**404 против 410.** `404` значит "нет и не было", `410` значит "было и удалено".
Обычное отсутствие ресурса по неизвестному идентификатору или имени (игра,
раздел форума, профиль, комментарий) отвечает `404`, даже когда запись скрыта
мягким удалением. Чтобы честно ответить `410`, сервис обязан отдельно проверить,
что строка существует, и такая проверка заводится осознанно, а не получается
сама собой. Осознанных случаев три: удаленный топик форума против никогда не
существовавшего, просроченный одноразовый токен из письма, истекшее приглашение.
Все прочее отвечает `404`.

Разнобой внутри одного ресурса запрещен отдельно. Если чтение отвечает `404` на
ненайденный комментарий, то правка и удаление отвечают тем же кодом: клиент
пишется по одному правилу на ресурс, а не по одному на действие.

**Отметка прочитанного — `DELETE <коллекция>/unread`.** Непрочитанное
моделируется подресурсом, а снятие метки — его удалением: операция идемпотентна,
повтор и повторная доставка запроса ничего не портят, и адрес обходится без
глагола в пути. Форма одна и та же для элемента (`.../{id}/unread`) и для всей
коллекции (`.../unread`). Заводить вместо этого `POST .../mark-read` нельзя: это
второе имя для того же действия.

**DELETE** возвращает `204 No Content` без тела.
Записанное исключение: `DELETE /v1/polls/{id}/vote` возвращает `200` с обновленным
`Envelope<Poll>` — клиент сразу перерисовывает результаты опроса без повторного запроса.

**Секрет никогда не едет в пути URL.** Путь пишется дословно в журнал доступа
обратного прокси, в лог запроса и в трейс, поэтому секрет в пути раскрыт по
построению, а его ротация — это чистка логов, а не смена переменной. Место
секрета — заголовок: у интеграции со своим соглашением берется ее заголовок
(`X-Telegram-Bot-Api-Secret-Token`), у прочих — `X-Dm-Webhook-Secret`. Сравнение
— `CryptographicOperations.FixedTimeEquals`, а незаданный секрет закрывает
эндпоинт, а не открывает его.

**Одноразовый токен из письма — тоже секрет.** Там, где владение токеном и есть
право на вызов (активация, сброс пароля, подтверждение смены почты, одобренная
смена логина, чтение гостевого обращения), токен — это учетные данные запроса, а
не часть адреса ресурса: он едет в заголовке `X-Dm-Account-Token`, у гостевого
обращения — в `X-Dm-Ticket-Token`, и одинаково у проверки статуса, и у вызова,
который завершает изменение. Делить их ("заголовок на GET, тело на POST") нельзя:
один сценарий получил бы два соглашения. Ссылка в письме по-прежнему ведет на
страницу клиента — она для человека, а не вызов API, и токен из нее клиент
перекладывает в заголовок. Отсутствующий, испорченный и неизвестный токен
отвечают одинаково: о том, почему ссылка не работает, вызывающий не узнает
ничего. Правило держит тест, обходящий контроллеры рефлексией.

**`CancellationToken` принимают только GET-экшены.** Мутация выполняется до
конца: многошаговые записи в слое хранения неатомарны (транзакция на весь слой
заводится в трех местах), поэтому отмена на середине оставляет половину записи
без отката и без следа — игру с временным публичным идентификатором, который
никто не пересчитает, или погашенное приглашение, оставшееся действительным.
Правило держит тест, обходящий контроллеры рефлексией. Разрыв соединения клиентом не
ошибка: `ErrorHandlingMiddleware` отвечает на него отдельной веткой, а не
записью уровня Critical.

**Заголовок `Location` у 201** указывает на созданный ресурс и ни на что другое.
Если у подресурса нет собственного адреса (нет `GET .../{childId}`), заголовок не
ставится вовсе — `201` без `Location` допустим, а `Location`, ведущий на коллекцию,
лжет: клиент, перешедший по нему, получит весь список вместо созданной записи.
Выбор между "завести адрес элемента" и "не ставить заголовок" делается по тому,
нужен ли этот адрес кому-то кроме заголовка.

## Pagination, Filtering & Sorting

### Принцип: Один endpoint — много сценариев

> **Правило:** Вместо специализированных endpoints (`/popular`, `/active`, `/owned`)
> используй **один list endpoint** с параметрами фильтрации и сортировки.

**Преимущества:**
- Меньше endpoints = проще API
- Гибкость для клиента
- Единая логика авторизации
- Кэширование по URL

### Pagination

| Тип | Параметры | Использование |
|-----|-----------|---------------|
| Offset | `?skip=20&take=10` | Списки с известным total |
| Cursor | `?cursor=abc&limit=50` | Бесконечный скролл |

**Границы страницы:** `take` — от 1 до 100, `skip` — неотрицателен. Значение вне
границ это ошибка валидации, а не молча урезанная страница: клиент, попросивший
тысячу, должен узнать, что столько не отдают, а не получить сотню и считать ее
полным набором. Верхняя граница обязательна для каждого списочного эндпоинта:
без нее один параметр в URL превращает список в выгрузку таблицы.

### Filtering

```
GET /v1/games?statuses=Active,Draft&hostUsernames=ivan&requiredTags=42
GET /v1/posts?gameId=abc&authorUsernames=ivan
GET /v1/users?role=moderator&isOnline=true
```

**Паттерны:**
- Enum фильтры: `?statuses=Active,Draft` (массив через запятую или повтор параметра)
- Boolean: `?isOpen=true`
- ID reference: `?gameId=abc`
- Числовые: `?minRating=5&maxPlayers=10`

### Словарь query-параметров

Одна задача — одно имя на всех эндпоинтах. Потребитель угадывает имя параметра
по аналогии с соседним списком, и угадывать он должен верно: неизвестный
параметр не отвергается, а молча игнорируется, так что опечатка в имени
возвращает `200` и полный список вместо отфильтрованного.

| Задача | Имя | Не писать |
|--------|-----|-----------|
| Полнотекстовый фильтр | `search` | `q`, `query`, `filter`, `text` |
| Страница по смещению | `skip` + `take` | `number` + `size`, `page`, `offset`, `pageSize` |
| Страница по курсору | `cursor` + `limit` | `after`, `nextCursor`, `count` |
| Граница даты | `<поле>FromUtc` / `<поле>ToUtc` | `<поле>After`/`Before`, голые `after`/`before` |
| Сортировка | `sortBy` + `sortOrder` | `sort`, `order`, `orderBy` |
| Логин пользователя | `username` / `authorUsername` | `user`, `login`, `author` |
| Статус модуля | `statuses` | `status` |
| Статус премодерации | `premoderationStatuses` | `premoderationStatus` |
| Кто ведет игру или блог | `hostUsernames` | `authorUsernames`, `masterUsernames` |

Последние три — про зеркальные списки. `/v1/games` и `/v1/blogs` отвечают на одни
и те же вопросы, и до сведения словаря отвечали разными именами: у игр `statuses`
списком, у блогов `status` скаляром, а фильтр по ведущим назывался
`authorUsernames` у игр и `hostUsernames` у блогов. Отдельно: "кто ведет" и "кто
написал" — разные фильтры, поэтому мастер игры не `authorUsername`.

**Число имени равно числу значений.** Повторяемый параметр — во множественном
(`statuses`, `authorUsernames`, `requiredTags`), одиночный — в единственном
(`status`, `authorUsername`, `role`). Множественное имя у скаляра — самая дорогая
ошибка словаря: имя совпадает с соседним эндпоинтом, а кодировка значения нет.

**Курсорная пагинация — не синоним смещенческой.** `cursor`/`limit` берут только
списки с keyset-обходом (чаты, глобальный чат, поиск сообщений). У остальных
`skip`/`take`, даже если страница на клиенте считается номером: номер в
смещение переводит клиент.

Правило держится тестом `QueryVocabularyShould`, который читает имена
`[FromQuery]`-параметров из сборки API.

### Sorting

```
GET /v1/games?sortBy=popularity&sortOrder=desc      # Popular = по подписчикам
GET /v1/games?sortBy=activated&sortOrder=desc       # Active = по дате активации
GET /v1/games?sortBy=created&sortOrder=desc         # Newest
GET /v1/posts?sortBy=rating&sortOrder=desc&take=1   # Best post
```

**Формат:** `?sortBy=<поле>&sortOrder=asc|desc` (default: `desc`).

**Допустимые поля** свои у каждого списочного эндпоинта, и перечислены они не здесь,
а рядом с самим эндпоинтом — в объявлении его параметра. Список в документе устаревает
молча; объявление рядом с кодом расходится с ним только через ревью.

**Неизвестное значение** — ошибка валидации, а не молча дефолтный порядок. Клиент,
попросивший сортировку, которой нет, должен узнать об этом, а не получить произвольный
порядок под видом запрошенного. То же и с направлением: все, что не `asc` и не `desc`,
отвергается, а не трактуется как `desc`.

### Примеры замены специальных endpoints

| Было (отдельный endpoint) | Стало (query parameters) |
|---------------------------|-------------------------|
| `GET /games/popular` | `GET /games?sortBy=popularity&take=10` |
| `GET /games/owned` | `GET /games?participating=true` |
| `GET /blogs/popular` | `GET /blogs?sortBy=popularity&take=10` |
| `GET /blogs/owned` | `GET /blogs?participating=true` |
| `GET /posts/best` | `GET /posts?sortBy=rating&take=1` |

> **`me` keyword:** Для текущего пользователя можно использовать `authorId=me`
> или отдельный флаг `?participating=true`.

### Когда отдельный endpoint оправдан

1. **Actions** (изменяют состояние): `/games/{id}/join`, `/posts/{id}/like`
2. **Агрегации** (сложные вычисления): `/statistics/overview`
3. **Специфичные форматы**: `/export/csv`

### Исключение: семантические шорткаты

Специализированный GET оправдан и тогда, когда его адрес называет устойчивое продуктовое
понятие ("лучшая публикация", "активный бан"), а не комбинацию фильтров: такой адрес
читается лучше, чем набор query-параметров. Поименного реестра таких адресов здесь нет
намеренно: список устаревает быстрее правила и ничем не проверяется, поэтому решение
принимается по критерию на ревью.

## Rate Limiting

| Эндпоинты | Лимит |
|-----------|-------|
| Глобальный | 100 req/min |
| Аутентификация | 5 req/min |
| Username check | 20 req/min |
| Email check | 10 req/min |
| Загрузка файлов | 10 req/min |
| Дорогие чтения | 30 req/min, скользящее окно |
| Личные разделы аккаунта | 60 req/min |

Счет ведется по аккаунту там, где запрос его несет, и по адресу вызывающего иначе. Гости
за общим адресом делят бюджет, вошедшие пользователи — нет. Глобальный лимит,
аутентификация и проверки занятости логина и почты считаются по адресу всегда: аккаунта у
такого запроса еще нет.

Выключенный лимитер политики не убирает: при `RateLimiting:Enabled=false` каждая из них
регистрируется как no-op, поэтому эндпоинт, просящий политику по имени, поднимается
одинаково в обоих режимах.

**При превышении:** `429 Too Many Requests` + заголовок `Retry-After`

## Кросс-доменные заголовки

В развернутом виде сайт и API отвечают с одного origin, а запуск из исходников
разводит их по разным портам, и там браузер спрашивает разрешение до самого
запроса. Разрешение состоит из двух перечней, и оба ведутся руками.

**Заголовки запроса.** Заголовок, которого нет в разрешении, не доезжает до
сервера вовсе: preflight отвечает без него, и браузер отменяет запрос целиком.
Поэтому новый заголовок вводится той же правкой, что и строка в разрешении, а не
после первого сообщения о том, что действие перестало работать.

**Заголовки ответа.** Коду страницы видны только заголовки безопасного списка;
все прочие приходят и молча недоступны. Значит заголовок, который клиент обязан
прочитать (`Location` у `201`, `Retry-After` у `429`), объявляется раскрытым
явно: необъявленный заголовок ответа равнозначен отсутствующему.

Топология развертывания эти правила не отменяет. Обратный прокси, ставящий SPA и
API на один адрес, прячет обе ошибки до дня, когда адреса разъедутся, поэтому
оба перечня закреплены тестом preflight, а не наблюдением за работающим стендом.

## Кеширование ответов

`Cache-Control: public` разрешен только для ответа, одинакового для всех: анонимного,
любого пользователя и любого значения `X-Dm-Audience`. Достаточно одного персонального
поля (счетчик непрочитанного, признак "мое"), чтобы ответ стал `private` — серверный
кеш и любой прокси ключуются по методу и пути, без `Vary`, и отдадут данные первого
запросившего всем остальным.

**Правило:** личное — `private`; общее и кешируемое — `public` плюс явный `Vary` на
каждый заголовок, от которого ответ зависит.

## Realtime (SignalR)

| Параметр | Значение |
|----------|----------|
| Endpoint | `/whatsup` |
| Протокол | WebSocket |
| Аутентификация | HttpOnly cookie сессии (та же, что у обычных запросов) |

**Особенности:**
- Receive-only (клиент не вызывает методы)
- Connection tracking — in-memory
- Адресация по connection ID (без групп)
- Токен в query-строке не принимается: URL попадает в логи прокси, а это
  обесценивает HttpOnly-куку, ради которой существует BFF
- Формат тот же, что у REST: `eventType` приходит именем события строкой, ключи
  `payload` — в camelCase. Хаб настраивается тем же JSON-контрактом, что и MVC;
  одно уведомление доезжает до вкладки двумя путями и не должно иметь двух
  написаний

```javascript
const connection = new signalR.HubConnectionBuilder()
  .withUrl("/whatsup", { withCredentials: true })
  .build();

connection.on("Send", (notification) => {
  console.log(notification.eventType, notification.payload);
});
```

## Rendering audience header (`X-Dm-Audience`)

Поля ответов, содержащие пользовательский BBCode, рендерятся сервером под запрошенный **audience**. Клиент передает желаемое намерение в HTTP-заголовке `X-Dm-Audience`; при отсутствии заголовка используется `display`.

| Значение | Назначение |
|---|---|
| `display` | Обычное чтение. Privacy-теги фильтруются по правам текущего пользователя. Default. |
| `author_edit` | Автор загружает свой контент в редактор. Сервер отдает HTML с `data-bb-*` round-trip атрибутами. Выдается только автору контента: авторство сверяется при рендере, остальным отдается `display`. |
| `plain_text` | Plain-text пайплайны. Privacy-теги вырезаются безусловно. |
| `embed_safe` | Link preview / cross-post embed. NSFW-safe tag set, privacy-теги вырезаются. |

Неизвестное значение заголовка трактуется как `display`. Контракт audience, правила видимости тегов, модель surface и permission-бакеты кэша — в [BBCODE_RENDERING.md](../architecture/BBCODE_RENDERING.md).
