# Паттерны и структура кода DM3

Куда класть код на сервере и в клиенте, как его называть и как раскладывать DTO. Держат тесты, названные у своих правил (в основном `test/DM.Architecture.Tests`), компилятор (правила Mapperly) и линтер клиента `src/DM.Web.Client/eslint.config.js` вместе с `src/DM.Web.Client/src/fsdBoundaries.spec.ts`. Правило без названной проверки не проверяется.

Единственный источник по структуре кода. Модуль здесь это доменный проект `DM.Domain.{Module}`, а не модуль в смысле глоссария (игра или блог).

## Паттерны по слоям

### Domain.Core / Shared Kernel

Общие контракты модулей: системные абстракции (`IDateTimeProvider`, `IGuidFactory`), контракты чтения чужой области (`IUserLookupService`), общие DTO, исключения и enums домена. Сервиса предметной области в ядре нет, допустимы только чистые политики и хелперы без состояния и обращений наружу (санитайзер разметки, кодирование публичного идентификатора, сравнение ролей). Все, чему нужны хранилище, сеть, часы или свое состояние, живет в модуле. У ядра нет ни одной ссылки на проект или пакет (`DomainBoundaryShould`).

Модуль не ссылается на соседний ни в одну сторону. Чужую область он читает синхронно только через контракт в ядре: потребность объявляет ядро, реализует модуль-владелец. Запись и побочные эффекты в чужой области (уведомление, начисление, рассылка) уходят доменным событием, и владелец сам решает, что с ним делать. Чтение держит `DomainBoundaryShould`, запись `CrossModuleContractShould`, отсутствие имен инфраструктуры в домене `DomainPurityShould`.

### Domain.* / Unified Services

Один сервис на фичу со всеми операциями над ней, а не `CreateGameService` и `UpdateGameService` по отдельности. Образцы `src/DM.Domain.Game/Features/Games/IGameService.cs` и его пара в API `src/DM.Web.API/Features/Game/Games/IGameApiService.cs`.

Доменный сервис владеет правилами: авторизация, инварианты, репозитории, события. API-сервис владеет формой HTTP-ответа: маппинг в DTO, конверт, сборка ответа из нескольких доменных вызовов, разрешение публичного идентификатора. Правило предметной области в API-сервисе и знание о DTO в доменном сервисе одинаково дефект. API-сервис нужен и как простой проброс: он держит форму ответа, когда меняется доменная сигнатура. Контроллер не зависит от абстракций `DM.Domain.*`, API-сервис от `DmDbContext` (`ServiceLayerBoundaryShould`), а весь HTTP-хост ходит к хранилищу только через домен (`HostStorageBoundaryShould`).

Интерфейс репозитория объявляет Domain, реализацию держит Infrastructure как `internal` (`src/DM.Domain.Game/Features/Games/IGameRepository.cs`, `src/DM.Infrastructure.Persistence/Repositories/Game/GameRepository.cs`). Репозиторий только читает и пишет данные, логика живет в сервисе.

### Infrastructure.* / Technical Concerns

Инфраструктура разложена по техническому назначению (кэш, разбор, хранилище, почта), а не по фичам. Группировка по модулям допустима только внутри технической папки. Бизнес-интерфейсы (`IGameService`, `ITopicRepository`) объявляет Domain.Core или Domain.*, Infrastructure объявляет только обертки над внешними библиотеками (`IBbParserProvider`). Тестом не проверяется.

### Web.API / Feature Folders

```
Features/{Module}/{Feature}/     # имя папки по разделу "Правила для папок Features"
├── {Entity}Controller.cs        # классы по сущности в единственном числе
├── I{Entity}ApiService.cs
├── {Entity}ApiService.cs
├── {Entity}Mapper.cs
└── {Entity}Dtos.cs
```

Например, `Features/Forum/Topics/` держит `TopicController`, `TopicApiService` и `TopicMapper`. DTO фичи собраны в один файл `{Entity}Dtos.cs`, кроме DTO уровней Ref, средний и Details, их держат отдельные файлы (образец в разделе DTO Projection Pattern). Тело запроса или ответа отдельной операции лежит своим файлом с именем операции (`{Операция}Request.cs`, `{Операция}Response.cs`), а не фичи: операций у фичи несколько.

Feature Folders это раскладка API-слоя, а не Vertical Slices, логика остается в Domain. `Features/` в домене значит бизнес-фичи, в Web.API папки фич API, а `features/` в клиенте это слой FSD.

### Workers / Event Handlers

Worker это отдельный процесс: consumer очереди, свои `Program.cs` и `Startup.cs`, письмо и уведомление уходят, не держа HTTP-ответ. Обработка разложена по техническому назначению: рендер письма, текст уведомления, документ для индекса. Правила предметной области (кто что может, что считается активным, когда начисляется награда) остаются в `Domain.*`, worker их вызывает.

Повтор сообщений worker подключает сам в своем `Startup.cs`, называя свою очередь (`AddDmRetryingConsumer`). Механизм повтора один на все workers, в `DM.Infrastructure.Messaging`.

### Frontend / Feature-Sliced Design (FSD)

Clean Architecture относится к серверу, клиент разложен по FSD:

Таблица идет от верхнего слоя к нижнему.

| Слой | Назначение |
|------|-----------|
| `app/` | Инициализация: Pinia, роутер, глобальные стили |
| `pages/` | Страницы роутера |
| `widgets/` | Крупные блоки, композиция features и entities |
| `features/` | Действия пользователя: формы, кнопки |
| `entities/` | Бизнес-сущности: store, api, ui |
| `shared/` | UI kit, HTTP-клиент, утилиты |

Слой импортирует только нижние. Слайсы одного слоя друг друга не импортируют, кроме двери `@x`. Транспорт API-клиента и кросс-доменные примитивы лежат в `shared/api`, доменный клиент в `entities/{x}/api`.

Типы в `shared/api/models` это зеркало контракта, а не удобная экрану форма: поле, обязательное на сервере, обязательно и в зеркале, даже если экрану удобнее держать там `null`. Разошедшееся зеркало не ловят ни типы, ни тесты, обе стороны верят своей копии, а человек видит форму, которая не сохраняется. Пустоту черновик выражает значением из контракта (пустой набор, пустая строка), а не подменой типа.

#### Публичный API слайса

- Слайс `entities/{x}`, `features/{x}`, `widgets/{x}` отдает наружу только barrel `index.ts`, импорт во внутренние файлы чужого слайса запрещен.
- У `pages/{x}` barrel нет: единственный потребитель страницы, роутер, адресует ее файл напрямую, иначе пропадает разбиение на чанки.
- Папка слайса названа его понятием в kebab-case и держит одну связную единицу.
- `*.spec.ts` лежит рядом с тестируемой единицей.

#### Единственное разрешенное исключение из запрета same-layer импортов: `@x`

```
entities/user/@x/game.ts        # что entities/game вправе взять из entities/user
entities/user/@x/moderation.ts  # что entities/moderation вправе взять из entities/user
```

Потребитель импортирует из `@/entities/user/@x/game`, а не из корня чужого слайса. Дверь адресная: файл назван слайсом-потребителем, и брать из нее вправе только он, этим она и отличается от второго публичного API. Реэкспортирует она только нужные символы.

Правила слоев проверяет линтер, а не ревью: `boundaries/dependencies` в `eslint.config.js` держит направление, barrel и адресность `@x`, динамический `import()` считается импортом, гейт `npm run lint:ci` идет в CI. Единственная лазейка мимо него это глобальная регистрация компонентов (`app/providers/components.ts`), у которой нет импорта. Поэтому глобально регистрируются только примитивы `shared` (`fsdBoundaries.spec.ts`).

#### Suffix `*Page` только у route-target

`*Page` носит только компонент, на который напрямую указывает роут верхнего уровня (`CreateGamePage`, `PulsePage`). Вкладка, секция или раздел внутри страницы суффикса не носит.

#### Окна

Окно называется `*Dialog`. Свою оболочку окна (фон, ловушку фокуса, Teleport) мимо примитива `Dialog` и композабла `useDialogShell` не пишут: копия расходится с ними при первой правке. Какое окно на чем строится, решает раздел "Dialog Standards" в [UI_STANDARDS.md](./UI_STANDARDS.md), поведение держит `dialogTier.spec.ts`.

#### Размещение пикеров и редакторов

- Поиск и выбор конкретной сущности живет в `entities/{x}`: композабл в `model/`, пикер в `ui/`.
- Композер без доменных сущностей (редактор, оболочка фильтров) живет в `shared/ui/` и получает доменные части слотом или пропом.

## Naming Conventions

### 1. Паттерн именования классов

Имя класса это `{Context}{Entity}{Suffix?}` в единственном числе: `UserProfile`, `GameCommentService`, `ModeratedProfileNote`. Суффикс называет тип (`Dto`, `Request`, `Service`, `Repository`).

### 2. Контексты (префиксы)

| Контекст | Значение | Пример |
|----------|----------|--------|
| без префикса | Базовая сущность | `User`, `Comment` |
| `Personal` | Данные текущего пользователя о себе | `PersonalProfile` |
| `User` | Публичное о любом пользователе и личное о другом | `UserProfile`, `UserProfileNote`, `UserBlacklist` |
| `Moderated` | Данные для модераторов | `ModeratedProfile`, `ModeratedProfileNote` |
| `Game` | Содержимое игры | `GameCommentService`, `GameBlacklist` |
| `Blog` | Содержимое блога | `BlogCommentService`, `BlogBlacklist` |
| `Publication` | Публикация в блоге | `PublicationCommentService` |
| `Topic` | Топик форума | `TopicCommentService` |

### 3. Распределение по модулям

Модуль выбирается вопросом "кто владеет данными".

| Вопрос | Модуль |
|--------|--------|
| Данные для входа и сессии? | Account |
| Данные текущего пользователя о себе? | Personal |
| Публичная информация о пользователях? | Community |
| Данные для модераторов? | Moderation |
| Данные конкретного содержимого? | Messaging, Game, Blog, Forum |

### 4. Правила для папок Features

Ресурс называется во множественном числе (`Profiles/`, `ProfileNotes/`, `Comments/`, `Blacklists/`, `Notepads/`), действие или процесс в единственном (`Authentication/`, `Registration/`, `Recovery/`, `Search/`). Запрещены `MyProfile` и `Self` (вместо них `Profiles/` в модуле Personal), а также `Blacklist` и `Notepad` в единственном числе.

### 5. Frontend (FSD), стиль именования

| Элемент | Стиль | Примеры |
|---------|-------|---------|
| Папки слайсов | kebab-case | `global-chat/`, `create-game/`, `game-post/` |
| Папки компонентов `shared/ui/` | PascalCase | `Button/`, `DataTable/` |
| Файлы компонентов Vue | PascalCase | `GameLink.vue`, `CharacterCard.vue` |
| Композаблы и утилиты | camelCase | `useDialogShell.ts` |

Компонент уровня модуля в `entities/{module}/ui` берет префикс модуля (`GameLink`), компонент под-сущности берет ее имя (`CharacterCard`, а не `GameCharacterCard`).

## DTO Projection Pattern (Expansion Hierarchy)

DTO ответа наследуют друг друга в три уровня: `{Entity}Ref` для сайдбаров и меню, `{Entity}` для таблиц и карточек, `{Entity}Details` для страницы. Образец `src/DM.Web.API/Features/Game/Games/` (`GameRef.cs`, `Game.cs`, `GameDetails.cs`).

1. Счетчики (`SubscribersCount`) есть на всех уровнях. Массивы (`Players`) добавляются к счетчикам, а не заменяют их.
2. Каждый уровень наследует предыдущий, на сервере классом, в клиенте интерфейсом (`interface Game extends GameRef`).
3. Расширяемый массив среднего уровня nullable, его могли не запросить. На уровне Details полный набор приходит всегда, и поле не nullable.
4. Пользователь в Ref и на среднем уровне это `UserRef`, полный `User` берется в Details.

```
GET /games?projection=ref   -> GameRef[]
GET /games                  -> Game[]
GET /games/{id}             -> Game
GET /games/{id}/details     -> GameDetails

UserRef -> User -> UserProfile -> PersonalProfile
                               -> ModeratedProfile
GameRef -> Game -> GameDetails
BlogRef -> Blog
```

## Целевые структуры (Блюпринт)

`{Placeholder}` обозначает переменную часть.

### DM.Domain.Core

```
DM.Domain.Core/
├── Enums/                # enums домена
└── {Concern}/            # интерфейсы, DTO и enums одной области контракта
```

Enums домена лежат в `DM.Domain.Core/Enums`: виды, статусы, роли, режимы доступа, настройки и параметры запроса (отбор, сортировка, обход). Словарь читают несколько модулей, а друг на друга они не ссылаются. Перечисление с одним читателем из `Enums/` тоже не выселяется: место объявления одно, и перечисление не переезжает через границу проекта, когда появляется второй читатель. Цена принята, теряется сигнал владения, и правка перечисления перекомпилирует все модули.

Вне `Enums/` ядро кладет перечисление по конвенции папки: намерение в `Authorization/`, значение опции в `Configuration/`, переход состояния в `Statuses/`, исход операции рядом с контрактом. Модуль держит перечисление у себя, только когда оно неотделимо от его контракта и никто больше его не читает (`{Entity}Intention`, исход операции, параметр своего запроса). Со вторым читателем оно переезжает в ядро.

### DM.Domain.{Module}

```
DM.Domain.{Module}/
├── Features/
│   └── {Feature}/
│       ├── I{Entity}Service.cs, {Entity}Service.cs
│       ├── I{Entity}Repository.cs
│       ├── {Entity}.cs                 # модель
│       ├── Create{Entity}.cs, Update{Entity}.cs     # команды
│       └── Create{Entity}Validator.cs, Update{Entity}Validator.cs
├── Authorization/
├── Configuration/
├── {Module}RegistrationExtensions.cs   # AddDm{Module}, когда скана мало
└── {Module}ConfigurationExtensions.cs  # когда модуль сам привязывает опции
```

Скан сборки (`AddDefaultTypes`) регистрирует каждый класс, все конструкторы которого публичны, и только заполняет пробелы: явную регистрацию он не заменяет, иначе пул, фабрики HTTP-клиентов и время жизни молча сменились бы на умолчания. Из скана тип выводится единственным способом, непубличным конструктором с комментарием о причине. Так делают, когда экземпляр строит рука или фабрика: класс с данными в аргументах, типизированный HTTP-клиент, форма ответа API. Иначе граф, проверяемый при старте (`ValidateOnBuild`), уронит хост.

Исключение: под-ресурс остается в папке родителя, когда выполнены оба условия. Путь чтения родителя сам заполняет производные значения под-ресурса, и каждая операция под-ресурса начинается с чтения родителя. Вынос тогда либо дает пару сервисов, зависящих друг от друга, которую контейнер не построит, либо разводит одно вычисление по двум местам. Под-ресурс, который только читает родителя, выносится обычным порядком. Исключение объявляется комментарием рядом с кодом, иначе следующий проход примет его за недоделанный вынос.

### DM.Infrastructure.{Name}

```
DM.Infrastructure.{Name}/
├── {Concern}/
│   └── {Module}/         # группировка по модулям внутри технической папки
├── Shared/
│   └── {Concern}/        # реализации cross-module контрактов Domain.Core
└── {Name}RegistrationExtensions.cs  # AddDm{Name}
```

В корне `DM.Infrastructure.Core` нет ничего, кроме папок и файла регистрации (`InfrastructureLayoutShould`).

### Завендоренный чужой код

Чужая библиотека, которую держим вместо пакета, лежит отдельным проектом в `src/`, а не папкой в потребителе: своя сборка не дает скану найти в ней второй ответ на наш интерфейс, а свои настройки компилятора разрешают ей то, чего нельзя нашему коду. К нашим правилам ее не приводят, любая правка может изменить то, что она делает с сохраненным текстом.

- Решение вендорить принимает владелец. Ссылка на репозиторий от агента или плана разрешением не является.
- Имя сборки не меняется.
- Ссылку на проект держит только обертывающий его слой инфраструктуры.
- Источник, лицензия, коммит и причина выбора объявлены в самом проекте, образец `src/BBCodeParser/BBCodeParser.csproj`.

### Словарь ошибок домена: коды HTTP, и это осознанно

Доменные сервисы бросают `HttpException` со статусом, а не свою таксономию отказов. Домен от этого не полностью транспортно-нейтрален: потребителю без HTTP-запроса статус в исключении не значит ничего. Плата принята: статус переводится в ответ в одном месте (`ErrorHandlingMiddleware`), а фоновые потребители решают судьбу отказа по самому исключению. Вторая таксономия окупится, когда статус понадобится прочитать вне HTTP-хоста, второму транспорту или worker'у, выбирающему по коду между повтором и отказом. Триггер проверяется грепом по чтениям `StatusCode`: пока вне обработки ошибок хоста их читает только домен, там, где отказ чужого поиска сам предметный ответ (пустой список, ноль, отсутствие записи, скрытый блог как ненайденный).

## Частые ошибки

### Запрос к удаленным записям пишется как обычный

Мягкое удаление скрыто глобальным фильтром запросов. Запрос, которому нужны удаленные строки (сборка мусора, отличие 404 от 410, восстановление), отключает фильтр явно, иначе молча не находит ничего.

### Порядок регистрации middleware

Компонент, читающий метаданные эндпоинта, стоит после маршрутизации, иначе работает вхолостую. Заголовки безопасности регистрируются первыми, иначе не попадут на ответы более ранних обработчиков (статика, документация). Ни сборка, ни тесты этого не видят.

### Курсорная страница по одной дате

Сортировка курсорной страницы тотальная, дата плюс id: по одной дате порядок одновременных записей выбирает план, и страницы дублируют или теряют строки. Предикат курсора это порядок (`id < курсор`), а не `id != курсор`, и окно вокруг записи сравнивается с курсором целиком. Форму `дата < X OR (дата = X AND id < Y)` PostgreSQL не превращает в диапазон индекса, и избыточная граница `дата <= X` рядом с ней возвращает курсор в `Index Cond`. Образец `src/DM.Infrastructure.Persistence/Repositories/Messaging/MessageRepository.cs`.

### Проверка внутри транзакции от гонки не защищает

Read committed не снимок. Решение по прочитанному держит ограничение базы, блокировка строки-владельца или токен версии, правило в [DATA_STORAGE.md](./DATA_STORAGE.md), раздел "Транзакция не снимок".

### Порядковый номер через MAX+1

Два одновременных создания читают один `MAX+1`, а счетчик в памяти теряет значение. Номер из постоянного URL держит уникальный индекс, а выдача сериализуется блокировкой строки-владельца (`FOR UPDATE`) в транзакции записи. Номера мягко удаленных записей не переиспользуются: их ссылки остаются 410.

### Несколько DbContext в одном scope

Scope отдает ровно один контекст (`DbContextScopeResolutionShould`), и контекст не потокобезопасен. Поэтому `Task.WhenAll` над двумя репозиториями одного scope запрещен, для параллельности нужен scope на ветку.

## Маппинг - Mapperly

Маппинги пишутся только на Riok.Mapperly, рантайм-маппера нет. Пакет подключается с `PrivateAssets="all"`, это генератор исходников. RMG012, RMG020 и RMG068 подняты до error в `.editorconfig`, и незамапленный член или неинлайнящаяся EF-проекция ломают сборку.

- Мапер это `[Mapper]` partial-класс рядом с фичей. Его зависимости (часы, текущий пользователь) приходят в конструктор, регистрирует его скан.
- Дозаполнение результата (например, `RenderContextEnvelope`) это именованный метод, вызванный явно после мапа. Неявных хуков нет.
- Общие конверсии это статические хелперы через `[UseStaticMapper(typeof({Helpers}))]`, для EF-проекций статические expression-хелперы (`AvatarProjections`, `GeneralUserProjections`), а не копии формул.
- EF-проекция это `static partial IQueryable<TDto> ProjectTo{Dto}(this IQueryable<TEntity>)` в статическом `[Mapper]`-классе, `TagWith` ставит вызывающая сторона. Проекция с вложенными пользователями или логикой запроса пишется явным `Select` в статическом классе `*Mappers` слоя хранения (`GameMappers`, `ForumMappers`): пользовательские методы Mapperly в queryable-проекцию не инлайнит. Правило для нескольких проекций живет одним полем `Expression` и вклеивается `ExpressionSplicer.Splice` (`PostPendencyFilters.OfRoom` в `GameMappers`). Непрозрачный метод в EF-проекции запрещен, он материализует строку целиком.
- В PATCH null в запросе значит "не прислали", а не "очистить", и write-маппинг сохраняет null.

## Что не используем

| Паттерн | Почему |
|---------|--------|
| MediatR | Хватает Unified Services, MediatR добавляет неявные зависимости |
| CQRS | Отдельной модели чтения нет |
| Event Sourcing | Нет требования воспроизводить каждое изменение |
| Specification Pattern | Нынешним запросам не нужен |
| BDD, SpecFlow | Хватает unit- и интеграционных тестов |
