# Система DM3

Из чего состоит система, как связаны слои и как ходят события. Тест или файл, который держит правило, назван рядом с ним. Конфигурацию работающего стенда и образы в реестре чтение дерева не проверяет.

## Коротко

DM3 это платформа для текстовых ролевых игр: игры, форум, блоги, личные сообщения,
глобальный чат, профили, модерация. Приложение одно. Доменные модули (Account, Personal,
Community, Moderation, Messaging, Game, Blog, Forum) работают в одном процессе:
`src/DM.Web.API` ссылается на все и он же разговаривает с браузером по HTTP.

**Источник истины PostgreSQL.** Схема общая, миграция единственная, один
`DmDbContext` держит таблицы всех модулей. В объектном хранилище лежат только байты
загруженных файлов. Почему СУБД одна и как пишутся пары хранилищ, описано в
[DATA_STORAGE.md](../conventions/DATA_STORAGE.md), вторую не дает поставить
компиляция (`test/DM.Infrastructure.Persistence.Tests/EntityStorageMarkerShould.cs`).

**Главное правило, событие не носитель факта.** Доменное событие сообщает о записи,
которая уже закоммичена, и не может быть единственным местом, где она существует.
Из него следует, почему публикация не роняет запрос, почему потребитель обязан быть
идемпотентным. На правило
ссылаются комментарии в коде и алертах (например `src/DM.Infrastructure.Mail/MailSender.cs`,
`src/DM.Infrastructure.Core/Tracing/MessagingMetrics.cs`, `docker/prometheus/alerts.yml`),
поэтому менять его в документе в одиночку нельзя.

### Топология рантайма

Развернутый стенд собирает сайт на один origin. Перед приложением стоит край на
nginx: раздает статику фронтенда, проксирует API и хаб, отдает файлы из объектного
хранилища, превью аватаров в том числе. Разбивка по префиксам лежит в
`docker/nginx/edge-locations.conf`, сам край появляется только в overlay
`docker/docker-compose.preview.yml`. Загрузка и отдача файлов описаны в
[UPLOADS.md](UPLOADS.md).

```mermaid
flowchart TB
    reader(["Читатель"])
    pop["Точка присутствия<br/>обратный прокси"]
    edge["Край сайта<br/>nginx"]
    spa["Фронтенд<br/>Vue 3, статика"]
    api["API<br/>ASP.NET Core + SignalR"]
    s3[("Объектное хранилище<br/>байты файлов")]
    pg[("PostgreSQL<br/>источник истины")]
    wmail["Воркер почты"]
    wnotify["Воркер уведомлений"]
    smtp["SMTP relay"]

    reader -->|"HTTP, WebSocket"| edge
    reader --> pop
    pop -->|"API, файлы и превью<br/>при промахе кэша"| edge
    edge -->|"/"| spa
    edge <-->|"/v1, /hubs (SignalR)"| api
    edge -->|"/dm-uploads"| s3
    api <-->|"пишет строки outbox,<br/>слушает realtime-push"| pg
    api --> s3
    wmail --> pg
    wnotify -->|"забирает события,<br/>шлет realtime-push"| pg
    wmail --> smtp
```

**Единый origin это свойство края, а не приложения.** Фронтенд просит `/v1`
относительно адреса, с которого загрузился (`docker/.env.example`). Базовый
`docker/docker-compose.yml` края и контейнера фронтенда не поднимает: dev-сервер
Vite ходит на API по абсолютному адресу из `VITE_API_HOST`, и работает CORS с
перечнем разрешенных источников (`src/DM.Web.API/Startup.cs`). Поэтому
кросс-доменная конфигурация проверяется только локально.

Наблюдаемость в схему не вынесена, она описана в
[MONITORING.md](../guides/MONITORING.md).

### Направление зависимостей

Стрелка означает ссылку проекта. Слой зависит только от слоев ниже. Фронтенд
говорит с API только по HTTP.

```mermaid
flowchart TB
    hosts["Хосты<br/>Web.API, Workers.Mail,<br/>Workers.NotificationDispatcher, Tools.Seeder"]
    infra["Инфраструктура<br/>Persistence, Messaging,<br/>Mail, Infrastructure.Core"]
    domain["DM.Domain.*, доменные модули"]
    core["DM.Domain.Core<br/>интерфейсы, DTO, enum, исключения"]

    hosts --> infra
    hosts -->|"все, кроме почтового воркера"| domain
    infra -->|"только Persistence"| domain
    infra --> core
    domain --> core

    classDef leaf fill:transparent,stroke-dasharray: 4 3
    class core leaf
```

У `Domain.Core` ссылок нет, он лист графа, и любая ссылка из него разворачивает
направление. Второй лист это завендоренный разбор BBCode (`src/BBCodeParser`): своя
сборка без ссылок, которую видит только оборачивающий ее Infrastructure.Core. Наши правки в ней есть,
каждая помечена в коде комментарием "DM3 addition against the original" рядом с местом
(`src/BBCodeParser/Tags/Tag.cs`). Правила
для такого кода и правило "бизнес-интерфейсы объявляет Domain" живут в
[PATTERNS.md](../conventions/PATTERNS.md).

| Слой | Может зависеть от | НЕ может зависеть от |
|------|-------------------|---------------------|
| Domain.Core | Только .NET BCL | Ничего из проекта |
| Завендоренная библиотека | Только .NET BCL | Ничего из проекта |
| Domain.* | Domain.Core | Других Domain.*, Infrastructure.* |
| Infrastructure.* | Domain.Core, Infrastructure.Core, Persistence еще Domain.* | Хостов |
| Хосты: Web.API, Workers.*, Tools.Seeder | Все | Ничего не запрещено |
| Web.Client | Только HTTP API | Backend напрямую |

Точный граф в csproj.

Доменная сборка не называет инфраструктуру ни одним именем. Правило проверяется по
ссылкам сборок, а не по тексту using: тип, взятый через алиас или полное имя, в тексте
не виден (`test/DM.Architecture.Tests/DomainPurityShould.cs`, `DomainBoundaryShould.cs`).

## Границы модулей

Правило границ модулей и вопрос "чьи это данные" живут в
[PATTERNS.md](../conventions/PATTERNS.md).

**Изоляция кончается на доменных модулях.** Схема общая, контекст один, Persistence
ссылается на все модули, и чтения через границу внутри этого слоя допущены
сознательно. Поэтому вынос модуля в отдельный сервис означает разделение схемы, а
не перенос кода.

**Модуль, который забыли зарегистрировать, компилируется и стартует** и отвечает 500
на первом запросе к своему эндпоинту. Хост собирает контейнер по списку маркерных
типов, написанному руками, и тест сверяет список с деревом
(`test/DM.Architecture.Tests/ModuleCompositionShould.cs`).

**Контейнер встроенный.** Почему не Autofac, записано в
[STACK.md](../STACK.md). Явное расширение `AddDmX(IServiceCollection)` есть у каждого
инфраструктурного проекта и у модуля, которому оно нужно, остальное приезжает сканом
сборки (`src/DM.Infrastructure.Core/Extensions/DefaultTypesRegistrationExtensions.cs`).
Скан только заполняет пробелы, поэтому явные регистрации идут раньше сканов, а
форвардинг-фабрики держат контракт "один инстанс на scope при нескольких
интерфейсах". Хосты включают `ValidateScopes` и `ValidateOnBuild`, и недостающая
регистрация падает при старте, а не на первом запросе. Сидер валидирует только
скоупы: его сканы тянут доменные сборки ради нескольких internal-типов и приводят
сервисы, которых он не резолвит (`test/DM.Architecture.Tests/CompositionRootShould.cs`).

## Жизненный цикл запроса

```
HTTP → конвейер middleware → контроллер → API-сервис → доменный сервис → репозиторий → PostgreSQL
```

Порядок конвейера задается в `src/DM.Web.API/Startup.cs` и здесь не копируется.
Обязательны четыре ограничения, каждое уже стоило дефекта.

- Разбор адреса клиента идет первым: лимитер, журнал входов и аудит читают адрес пира.
- Заголовки безопасности стоят выше всего, что пишет ответ, иначе ответы ранних
  обработчиков уходят без них.
- CORS стоит выше кеша ответов, иначе в кеш ложится ответ без CORS, и браузер
  роняет чужой 200 на все время жизни записи.
- Все, что читает метаданные эндпоинта (лимитер, авторизация), идет после
  маршрутизации, выше нее атрибуты политик инертны.

Сессия живет в куке HttpOnly, токена в JavaScript нет. Защиту от подделки
межсайтового запроса дают `SameSite=Lax` и проверка origin
(`src/DM.Web.API/Middleware/CsrfProtectionMiddleware.cs`), чеклист в
[SECURITY.md](../conventions/SECURITY.md#защита-от-атак-чеклист). Лимитер считает по
аккаунту, а имя аккаунта кладет на контекст отдельное звено, читающее только куку:
партиционер зовется синхронно и раньше, чем появилась личность. Поломка этой пары
молча переводит счет на адрес (`test/DM.Architecture.Tests/RateLimitPipelineShould.cs`).

**Хост не ходит в хранилища сам, включая фоновые задания.** Иначе продуктовое
правило (что считать популярностью, сколько живет токен) существует только в
работающем процессе, и его нельзя позвать со стороны и покрыть доменным тестом.
Исключения названы поименно, это композиционный корень и прогрев
(`test/DM.Architecture.Tests/HostStorageBoundaryShould.cs`).

**Репозиторий, который пишет дважды, пишет оба раза или ни одного.** Две записи без
обертки это две транзакции, и в зазоре живет состояние без имени: пароль сменен, а
погасивший его токен еще действует (`test/DM.Architecture.Tests/DurableWritesShould.cs`).

Формат ответов и ошибок описан в [API_DESIGN.md](../conventions/API_DESIGN.md).
Конверт клиент снимает единственным помощником
(`src/DM.Web.Client/src/shared/api/envelope.ts`).

## Конвейер доменных событий

События нужны, чтобы модули не знали друг о друге, а отправка письма не держала
HTTP-ответ.

```
доменная запись (коммит) → INSERT в OutboxEvents (второй коммит)
                                   ↓ захват строки, опрос раз в секунду
                             воркер уведомлений
```

**Публикация это вставка строки.** `SendAsync` пишет строку в OutboxEvents той же
PostgreSQL вторым коммитом сразу после доменного, своей транзакции не открывает и в
чужую не входит (`src/DM.Infrastructure.Persistence/RelationalStorage/OutboxEventProducer.cs`,
`test/DM.Architecture.Tests/EventOutboxShould.cs`). После коммита вставки доставка
at-least-once, и остановленный воркер означает задержку, а не потерю. Окно потери
остается: kill процесса между двумя коммитами и отказ самой вставки. Поэтому то, что
обязано случиться, должно быть восстановимо из состояния базы.

**Отказ вставки не роняет вызывающего.** Иначе закоммиченная запись превратилась бы в
ошибку, и клиент повторил бы ее второй раз. Продюсер сам логирует отказ и считает
метрикой, в местах вызова try и catch нет. Событие не публикуется раньше своего
коммита (`test/DM.Architecture.Tests/PublishAfterCommitShould.cs`).

**Воркер уведомлений берет события прямо из таблицы.** Раз в секунду он захватывает
самую старую готовую строку своей очереди под `FOR UPDATE SKIP LOCKED` и держит
транзакцию захвата открытой, пока обработчик не вернется. Два цикла не
берут одну строку и не ждут друг друга. Строка помечается обработанной только после
успеха обработчика, а пока строки готовы, цикл выгребает дальше. Строку типа, которого
сборка воркера не знает, он не захватывает (`src/DM.Infrastructure.Messaging/Queues/QueueWorker.cs`,
`src/DM.Workers.NotificationDispatcher/NotificationQueue.cs`).

**Строка, которая не прошла, не держит очередь.** Исключение обработчика тратит попытку,
и строка ждет растущую паузу лестницы повторов, а цикл тем временем берет строки за ней.
Последняя попытка делает строку мертвой. Ответ обработчика, что строку обработать нельзя,
делает ее мертвой сразу. Остановка хоста и ошибка самого цикла (захват, отметка,
соединение) попытку не тратят, после ошибки цикл ждет свою растущую паузу и не выходит,
иначе остановился бы весь хост. Мертвую строку возвращает одна команда базы
(`src/DM.Infrastructure.Core/Queues/DeadRows.cs`), обработанные и мертвые строки удаляет
очистка по сроку от отметки, а ждущую и повторяемую не удаляет никогда
(`src/DM.Infrastructure.Persistence/RelationalStorage/RetentionSweeper.cs`).

**Доставка из очереди тоже at-least-once**, поэтому обработка с побочным эффектом
идемпотентна. EventId проставляется в единственной точке публикации и одинаков на
всех повторах, а воркер уведомлений пишет по паре (EventId, тип уведомления) под
уникальным индексом. Пустой EventId обрабатывается без дедупликации
(`src/DM.Workers.NotificationDispatcher/Dispatching/NotificationProcessor.cs`).

**Письмо ждет в той же таблице** строкой почтовой очереди. Отправитель
писем проверяет письмо и пишет строку одной командой через источник соединений
процесса, а не через трекер изменений запроса, и вызывающий зовет его после своего
коммита. Отказ вставки, в отличие от события, бросается вызывающему: письмо активации
и сброса пароля из базы не восстановить, и ошибку запроса читатель повторит сам
(`src/DM.Infrastructure.Mail/MailSender.cs`). Почтовый воркер выгребает свою очередь
тем же циклом, что и воркер уведомлений. Отказ почтового сервера тратит попытку, и
письмо уходит с первой попытки после его возвращения. Текст, который не читается как
письмо, делает строку мертвой сразу. Успех стирает текст письма той же командой, что
ставит отметку (`src/DM.Workers.Mail/MailQueue.cs`).

Транспорта нет: очередь это та же таблица и свой тонкий цикл
(`src/DM.Infrastructure.Messaging/Queues`), без брокера и библиотеки очередей.
Почему, записано в [STACK.md](../STACK.md). Пересматривать, если понадобятся саги
или несколько транспортов.

## Уведомления

```mermaid
flowchart LR
    ev["Событие из очереди"] --> gen["Генераторы уведомлений"]
    gen -->|"сказать пользователю"| pg[("PostgreSQL<br/>список уведомлений")]
    pg --> mail["письмо / бот<br/>по подписке"]
    pg --> push["realtime-push:<br/>уведомлением базы в API,<br/>оттуда в хаб SignalR"]
    gen -->|"лишь обновить бейдж"| push
    push --> fe["Открытая вкладка"]
```

Уведомление, которое читают списком, сохраняется и может уйти письмом или ботом.
Событие, которое лишь просит вкладку перечитать счетчик, идет тем же путем, но не
сохраняется и в письмо не попадает.

Каналы доставки читают то, что вернула запись, а не то, что ей передали: сервис
сужает круг получателей, и рассылка по исходному списку доставила бы то, что фильтр
отказался хранить. Доставка после записи идет best effort, исключение отсюда вернуло
бы обработку в повторы и переписало бы сохраненное
(`src/DM.Workers.NotificationDispatcher/Dispatching/NotificationProcessor.cs`).

Слова и адрес уведомления живут одной таблицей в домене
(`src/DM.Domain.Personal/Features/Notifications/NotificationWording.cs`,
`NotificationDestination.cs`), ее читают и воркер, и API, поэтому письмо, бот и
вкладка называют событие одинаково и ведут на одну страницу. Строку списка и push
собирает один маппер API (`src/DM.Web.API/Features/Personal/Notifications/NotificationMapper.cs`).
Порядок сведений, прочитанных из базы, не тот, в котором их записал генератор: сумка
лежит в jsonb, а он порядка ключей не держит.
Поэтому место, куда ведет строка, сервер отмечает у сведения признаком
(`isDestination`), и клиент берет его, а не первое место по порядку.
Клиент событий не называет и путей не строит
(`test/DM.Architecture.Tests/NotificationVocabularyShould.cs`,
`NotificationLinkVocabularyShould.cs`).

Кому уходит уведомление о записи модерации, решает то же правило, что ее чтение:
уведомление не ведет туда, где получателя ждет 404
([AUTHORIZATION.md](AUTHORIZATION.md#обращения)).

Обратный путь до браузера идет через уведомления базы: воркер шлет push в канал
базы, слушатель каждого экземпляра API слышит его своим соединением и отдает в хаб.
Push не хранится, это копия сохраненного уведомления, и пропущенный при
переподключении push вкладка наверстает при перезагрузке
(`src/DM.Web.API/Realtime/PushListener.cs`).

## Разметка: рендер только на сервере

Текст пользователя хранится как BBCode, в HTML его превращает только сервер, клиент
получает готовую разметку. Разбор, теги и видимость описаны в
[BBCODE_RENDERING.md](BBCODE_RENDERING.md).

**Скрывающий блок закрывается только своим тегом.** Закрывающий тег чужого имени
внутри `[private]` не закрывает ничего, иначе обычная ошибка вложенности печатала бы
остаток скрытого блока всей комнате. На `[mod]` признака нет: он публичен на чтение,
и раннее закрытие стоит только форматирования (`src/BBCodeParser/Tags/Tag.cs`,
`src/DM.Infrastructure.Core/Parsing/BbParserProvider.cs`).

## Адреса сайта

Экземпляр приложения один, дополнительный адрес обслуживает точка присутствия
([POINT_OF_PRESENCE.md](../guides/POINT_OF_PRESENCE.md), там же общий вход между
адресами). Область куки сессии задает развертывание
([CONFIGURATION.md](../references/CONFIGURATION.md#область-куки-сессии)), а выдача и снятие куки обязаны идти через один помощник: браузер заменяет куку только
при совпадении атрибутов, и разошедшийся Domain оставляет сессию, которую выход не
гасит (`src/DM.Web.API/Shared/Authentication/ApiCredentialsStorage.cs`).
