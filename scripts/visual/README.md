# Стенд кадров и снимок ответов API

Два инструмента, которые отвечают на вопрос "правка невидима?": кадры страниц и
снимок ответов API. По умолчанию оба меряют уже запущенный стенд, тот самый, с
которым работает сайт на 5173, и ничего в нем не меняют: ни сброса, ни
пересборки, ни сида. Сам инструмент в базу не пишет, стенд меняют только его
входы и просмотры, как у любого посетителя (ниже). Docker он только спрашивает:
запущен ли API, выключены ли лимиты, не пересоздали ли стенд во время прогона.

В CI не входят: пиксели зависят от шрифтов и растеризатора машины, базу сравнивают
только на той машине, где ее сняли. Базы в репозиторий не кладутся.

## Команды

Из корня репозитория:

```
node scripts/visual/visual.mjs stand
node scripts/visual/visual.mjs snap <метка> [--rev REV] [--root DIR] [--theme dark]
node scripts/visual/visual.mjs diff <метка> [--rev REV] [--root DIR] [--theme dark]
node scripts/visual/visual.mjs api-snap <метка> [--rev REV] [--root DIR]
node scripts/visual/visual.mjs api-diff <метка> [--rev REV] [--root DIR]
```

`stand` проверяет стенд и печатает его отпечаток. `snap` снимает базу, `diff`
сравнивает с ней. Коды: 0 совпало, 1 есть разница, 2 отказ до прогона (причина в
выводе), 3 прогон недействителен.

## Как снять базу

Стенд поднят и засеян (`dm.ps1 start`, `dm.ps1 seed`), лимиты запросов выключены.
Лимиты выключает `dm.ps1 e2e`: он пересоздает только API, данные остаются. Перед
снимком инструмент проверяет, что API отвечает (`GET /v1/games?page=1`) и сид на
месте, и читает лимиты с контейнера `dm-api`. Лимиты включены: отказ. Прочитать
нельзя (нет docker, API запущен не в контейнере): предупреждение, а 429 во время
прогона делает его недействительным.

Порядок для шага: до правки `snap <метка> --rev HEAD` и `api-snap <метка> --rev HEAD`,
после правки `diff <метка>` и `api-diff <метка>` по рабочему дереву.

`--rev` (он же `--commit`) собирает клиент из коммита, выгруженного `git archive` в
отдельный каталог, а не из рабочего дерева. Это и естественная база шага, и
единственное дерево, которое никто не правит во время прогона: рабочее дерево
общее, и чужая временная правка исходника (прогон "тест падает на сломанном")
попадет в сборку. Сервер при этом тот, что запущен. Для правки сервера API между
`snap` и `diff` пересобирается из дерева командой `dm.ps1 e2e`, данные остаются.

Клиент собирается в отдельный каталог (`dist/` и сервер владельца на 5173 не
трогаются) и поднимается `vite preview` на 5174. Порт должен быть свободен: API
пускает браузер только с 5173 и 5174, на другой порт переехать нельзя.

`--no-build` берет прошлую сборку клиента. `--grep RE` ограничивает состояния (или
маршруты API, выражение сверяется с "[проект] › файл › состояние"). Такой прогон
сравним с полной базой только по состояниям гостя: остальные оставляют следы
(открытая тема становится прочитанной), и порядок прогона на них влияет.
`--no-stand` из прежних команд принимается и ничего не меняет.

## Отпечаток данных и пересев

Две базы сравнимы только на одних и тех же данных, поэтому `meta.json` базы
хранит отпечаток стенда: итоги `GET /v1/stats` (пользователи, персонажи, игры,
посты, блоги, публикации) и дату регистрации SolohinLex. Сид раскладывает даты от
момента, когда его запустили, и пересев сдвигает эту дату, даже если итоги
совпали. Новая игра, пост или аккаунт сдвигают итог.

`diff` и `api-diff` сверяют отпечаток до прогона. Не совпал: сравнения не будет
(код 2), вывод перечисляет, что изменилось. Значит, стенд пересеян или в него
писали, и базу надо снять заново теми же `snap` и `api-snap` с той же меткой. База
от прежней версии инструмента отпечатка не имеет и тоже отклоняется. После
прогона отпечаток снимается еще раз: изменился за время прогона, и результат
недействителен (код 3).

## Шум запущенного стенда

Отпечаток не видит того, что прогон оставляет сам: входы ролей (сеансы, история
входов, последняя активность) и прочитанное. Первый прогон после сида видит
непрочитанное, следующие уже нет, поэтому после сида первый `snap` пробный, а
базой служит второй. Сеансы и журнал безопасности прибавляют по строке за вход, а
списки по последней активности (превью подписчиков) ставят аккаунты стенда в
порядке, в каком их последним впустил инструмент. Это сворачивается по реестру
`api-volatile.mjs`: строки входов прогона, одинаковые без времени и id, остаются по
одной (и в снимке ответов, и в ответах странице), аккаунты стенда в таких списках
идут по имени на своих местах. Расходится то, что делали на сайте между базой и
сравнением, если итоги от этого не сдвинулись. Такие различия видны по именам состояний и маршрутов. Вердикт без
этого шума дает только пересобранный стенд.

## Пересобранный стенд: --rebuild-stand

Прежнее поведение, только по явному флагу. Он уничтожает данные общего стенда и
выключает сайт на 5173 на 10-15 минут. Перед этим инструмент печатает
предупреждение и ждет 10 секунд, Ctrl+C отменяет.

`dm.ps1 reset` поднимает стек, затем API и воркеры останавливаются, база создается
заново из миграции, в нее пишется сид с закрепленными эпохой `2026-06-15T12:00:00Z`
и зерном `20260730` (как в `scripts/verify-seed-reproducibility.sh`), и только потом
API и воркеры стартуют со своим оверлеем. Порядок важен: периодические задачи API,
успевшие пройти до сида или в его середине, сдвигали номера тем и идентификаторы,
и один и тот же сид выходил разным. В оверлее, как в `dm.ps1 e2e`, выключены лимиты
запросов, и последняя активность аккаунта ставится только при входе: иначе списки
по активности (читатели игры) упорядочивали аккаунты стенда по тому, какой из них
случайно спросил последним. С `--rev` из коммита собирается и стек.

Два прогона одного коммита на таком стенде дают одинаковые байты. База, снятая с
флагом, сравнима только с прогоном с флагом, и наоборот. Смешать режимы
инструмент не даст и откажет до пересборки. `stand --rebuild-stand` только
пересобирает стенд.

## Где что лежит

По умолчанию базы в `%TEMP%/dm3-visual/frames/<метка>/<тема>/` и
`%TEMP%/dm3-visual/api/<метка>/`, другое место задает `--root`. Отчет `diff`
лежит рядом с базой в `<метка>.diff/`: `report.txt` по состояниям, кадры
`-actual`/`-diff`, для дерева и стилей файлы `.actual` и готовый `.diff`.

## Что снимается

Кадры: состояния гостя, участника, наставника, модератора, старшего модератора и
администратора, список в `states.ts`. Две ширины: 1920×911 (окно владельца, монитор 1920×1080 при масштабе 100%) и телефон 390×844 при
плотности 3 с эмуляцией телефона. Окно растягивается на высоту страницы (до
предела в `frames.spec.ts`: длиннее браузер одним куском не рисует, остаток
страницы виден только в дереве и стилях), у плавающего (окна, меню, подсказки,
выбор даты) остается настоящим. Три канала:

- PNG через `toHaveScreenshot`, `maxDiffPixels: 0`, анимации выключены, курсор
  скрыт; порог цвета пропускает отличие в одну единицу канала (сглаживание края
  растеризатор между запусками браузера рисует на единицу светлее или темнее);
- дерево: body по узлу на строку, атрибуты по алфавиту, без `data-v-*`,
  комментариев и случайных id, текстовые узлы в кавычках (виден потерянный
  пробел между строчными элементами);
- вычисленный стиль ключевых узлов (теги и роли, а не классы) с `::before` и
  `::after`.

Если дерево разошлось только в атрибутах `class`, отчет пишет "только class".

Закреплено в странице: часы стоят на эпохе `2026-06-15T12:00:00Z` (`page.clock`), и
на запущенном стенде тоже, хотя его сид разложен от другого дня: базе и сравнению
важно, что часы одни. `Math.random` и `crypto.randomUUID` детерминированы, запросы
в интернет отклоняются, вопрос о часовом поясе отвечен (кроме своего состояния).
Перед съемкой дерево должно простоять без изменений 2,5 секунды: короткие эффекты
на таймерах страницы (подсветка поста при открытии комнаты) успевают закончиться.
Если API запущен в контейнере, прогон ждет первых проходов его периодических задач
после старта: они пишут в базу по незакрепленным часам сервера.

API: все GET из `artifacts/openapi-routes.json` от гостя, участника (TestUser) и
модератора (TestModerator), нормализованный JSON по файлу на маршрут и роль.
Параметры пути заполняет `api-fixture.mjs` по спискам самого API; GET без строки
там попадает в отчет как "не спрошен", и снимок не проходит.

## Маски и изменчивые поля

То, что меняется между прогонами одного коммита и не закрепляется, внесено в
реестры с причиной у каждой записи: `masks.ts` для кадров, `api-volatile.mjs`
для ответов (поля, куски строк и списки, которые сервер отдает без порядка).
Запись прячет изменения этого места, поэтому новая появляется только после того,
как закрепить не вышло, и только с доводом. Записи о списках без порядка
описывают дефекты сервера и уходят вместе с ними.

## Когда что-то не сходится

- `BROKEN` в отчете: состояние не открылось (кнопку переименовали, страница
  упала). Поправить `states.ts` или код. `BROKEN` с 429 значит включенные лимиты.
- `DIFFERS`: смотреть `-diff.png` и `.diff` рядом с отчетом.
- Код 2: отказ до прогона. Стенд не отвечает или не засеян, включены лимиты, база
  снята в другом режиме или на других данных.
- Код 3: прогон недействителен. Во время него стенд пересоздали (e2e,
  `dm.ps1 reset`, `verify-seed-reproducibility.sh`), изменились его данные, снимку
  ответов API ответили 429, либо в рабочем дереве записали исходник, из которого
  собирались клиент или стенд (без `--rev`). Стенд и дерево общие: на время
  прогона их никто больше трогать не должен.
