# Рефакторинг в рамках

## Правила, на которых стоит порядок

- Вердикт проверки дает код возврата команды, а не хвост вывода. Ненулевой код читается до вердикта: какая команда его вернула и о чем она отвечает.
- Тест, который заменяет убранный, проверяется на сломанном коде: прежняя версия файла возвращается из истории, и тест обязан упасть на своем утверждении. Способ описан в разделе [тест обязан падать на сломанном коде](../../../docs/conventions/PROCESS.md#тест-обязан-падать-на-сломанном-коде).
- Сборка и тестовая база общие. Прогон не идет одновременно с чужим, а массовое падение читается как дефект только после проверки, что рядом не шел второй прогон.
- `git stash`, `checkout`, `restore`, `reset` и `clean` агенту запрещены. HEAD остается началом задачи, а база и откат шага берутся из копии его файлов (шаг 3).

## Порядок

1. Записать рамки: файлы из задания и то, что остается прежним (вид, ответы сервера, поведение). Файл вне списка не правится, нужное в нем идет в отчет строкой "файл:строка, что". Если перенос ломает путь, по которому файл читают гейт-реестр или тест, а их нет в списке, шаг не делается.
2. Если задание поручает стенд, до первой правки снять его базу: `node scripts/visual/visual.mjs snap <метка> --rev HEAD` и `node scripts/visual/visual.mjs api-snap <метка> --rev HEAD`. Инструмент меряет уже запущенный стенд и ничего в нем не пересобирает. Условия, при которых снимок сравним, описаны в [scripts/visual/README.md](../../../scripts/visual/README.md), и читается он до первого снимка.
3. Перед каждым шагом затронутые им файлы копируются в scratchpad с раскладкой репозитория, из корня в Git Bash: `cp --parents <пути> <scratchpad>/<шаг>/`. Копия служит откатом шага и базой его сравнения по токенам, а сборку до шага сохраняет сам инструмент сравнения (шаг 5.3). Шаг, который не прошел, не чинится сверху новыми правками: он откатывается (`cp -r <scratchpad>/<шаг>/. .` из корня, созданные шагом файлы удаляются) и делится на шаги поменьше.
4. Шаги маленькие, в шаге один вид правки. Перенос и чистка идут отдельными шагами: при переносе код не переписывается, и сравнение показывает чистый перенос, а чистка следующим шагом видна своим диффом.
5. Каждый шаг доказан, от дешевого к дорогому:
   1. Компилятор и линт. Клиент, из `src/DM.Web.Client`: `npm run type-check` (четыре конфига, спеки и e2e в их числе) и `npx eslint --max-warnings 0 <файлы>`. Сервер, из корня: `dotnet build DM.sln`, предупреждение там ошибка.
   2. Тесты затронутого: из `src/DM.Web.Client` `npx vitest run <спеки и гейты-реестры>`, из корня `dotnet test <тестовый проект>` по затронутым модулям.
   3. Сравнение кода шага, из корня. Перенос на клиенте сравнивается сборкой: до шага `node scripts/visual/compare-code.mjs --build --base-dir src/DM.Web.Client --save-base <scratchpad>/<шаг>-build --base-only` сохраняет сборку дерева, после шага `node scripts/visual/compare-code.mjs --build --baseline <scratchpad>/<шаг>-build` сравнивает с ней рабочее дерево. Правка одних стилей идет так же через `node scripts/visual/compare-css.mjs` с `--base-dir`, `--save-base <файл> --base-only` и `--baseline <файл>`. Правка комментариев сравнивается по токенам, а база в этом режиме только ревизия. Поэтому сначала `node scripts/visual/compare-code.mjs --head-dir <scratchpad>/<шаг> -- <пути>` показывает, что до шага файлы совпадали с HEAD по коду, и тогда `node scripts/visual/compare-code.mjs -- <пути>` сравнивает сам шаг. Если прежний шаг уже менял код этих файлов, по токенам шаг не сравнить, поэтому правка комментариев ставится раньше чистки тех же файлов.
   4. Стенд, если задание его поручает: `node scripts/visual/visual.mjs diff <метка>` по рабочему дереву для того, что рисуется. Ответы сервера `api-diff <метка>` берет у запущенного API, и серверную правку он доказывает только после пересборки API из дерева (`dm.ps1 e2e`, данные остаются), когда задание эту пересборку поручает. Без пересборки серверная правка не доказана, и так и пишется в отчете.
6. Неиспользуемое ищет компилятор, а не поиск по тексту. Поиск по тексту находит имя в комментарии, в строке и у чужого символа с тем же именем и не видит ссылку через реэкспорт. Список неиспользуемого до и после шага сокращается ровно на удаленное.
   - Клиент, из `src/DM.Web.Client`: `npx vue-tsc --noEmit -p tsconfig.app.json --composite false --noUnusedLocals --noUnusedParameters`, и так же по `tsconfig.vitest.json` для спеков. Неиспользуемые экспорты он не видит, их ищет разбор импортов и экспортов через TypeScript API, включая блоки `<script>` компонентов.
   - Сервер: анализаторы IDE0051, IDE0052 и IDE0060. В репозитории их уровень не поднят, а `dotnet format style` из трех видит только IDE0060, поэтому уровень поднимается на время прогона двумя файлами в scratchpad, без правки `.editorconfig`. Файл `unused.globalconfig`:

     ```
     is_global = true
     dotnet_diagnostic.IDE0051.severity = warning
     dotnet_diagnostic.IDE0052.severity = warning
     dotnet_diagnostic.IDE0060.severity = warning
     ```

     Файл `unused.targets` рядом с ним:

     ```xml
     <Project>
       <PropertyGroup>
         <WarningsNotAsErrors>$(WarningsNotAsErrors);IDE0051;IDE0052;IDE0060</WarningsNotAsErrors>
       </PropertyGroup>
       <ItemGroup>
         <EditorConfigFiles Include="$(MSBuildThisFileDirectory)unused.globalconfig" />
       </ItemGroup>
     </Project>
     ```

     Прогон из корня: `dotnet build <проект> --no-incremental -p:EnforceCodeStyleInBuild=true -p:CustomBeforeMicrosoftCommonTargets=<полный путь к unused.targets>`. Находки идут предупреждениями и код возврата не меняют, поэтому результатом здесь служит список строк IDE0051, IDE0052 и IDE0060 из вывода. Без `--no-incremental` проект, который не пересобирался, своих находок не печатает, и список "после" выходит короче настоящего. Неприватное эти анализаторы не видят, его ищет поиск ссылок по семантической модели.
   - То, до чего добираются по строке (маршрут, регистрация через рефлексию, путь в тесте, `vi.mock`, ссылка шаблона `ref="..."`), компилятор не видит, а переменную, на которую шаблон ссылается через `ref="..."`, `vue-tsc` прямо называет неиспользуемой. Удаление такого помечается в отчете "не доказано до полного прогона волны": полные сюиты в шаге не гоняются.
7. Слияние модулей делается, только когда задание называет, что с чем сливается и какой интерфейс остается. Слияние меняет границы и интерфейс, и это решение оркестратора, а не исполнителя. Довод для него дает тест удаления: мысленно убрать модуль. Если сложность исчезла, модуль был транзитным и вливается в соседа. Если она расползлась по вызывающим, модуль оправдан и остается. Исполнитель, который видит, что решение задания этот тест не проходит, пишет об этом в отчет, а не меняет решение. У слитого модуля узкий интерфейс: наружу только то, что зовут вызывающие, тесты идут через этот интерфейс и заменяют тесты мелких частей, а не наслаиваются на них. Сравнение до и после такой шаг не доказывает, поэтому он закрывается ревью свежего агента на модели по правилу в [CLAUDE.md](../../CLAUDE.md), и до ревью слияние не готово.

## Отчет

По каждому шагу: что сделано, файлы, команды доказательства с кодами возврата, для удаления неиспользуемого списки до и после. Отдельно: нужное в чужих файлах, удаленные файлы, удаления с пометкой "не доказано до полного прогона волны", серверные правки без пересборки API, шаги слияния, ждущие ревью, модель и глубина мышления, на которых шел агент.

## Границы

- Поведение и вид не меняются, даже когда правка очевидно лучше: такое уходит в отчет кандидатом.
- Тест, который перенос или слияние убирает, заменяется проверкой не слабее, и она проверяется на сломанном коде.
- Стенд, сброс, сид и пересборка API только по прямому поручению задания.
